## 3. 失败用例与根因

### 3.1 三条失败同源：`ymd()` 用 `Math.round` 取"天数"

| 用例 | 断言 | 实测 | 差异 |
|---|---|---|---|
| LT-26-今天 | `1 天` | `不到 1 天` | −1 |
| LT-26-昨天 | `2 天` | `1 天` | −1 |
| LT-26-7 天前 | `8 天` | `7 天` | −1 |
| LT-27-2020-02-29 | `6 年 8 个月 10 天` | `6 年 8 个月 9 天` | −1 天 |
| LT-27-2023-01-31 | `3 年 9 个月 7 天` | `3 年 9 个月 6 天` | −1 天 |
| LT-28 内置 2018-04-22 | `8 年 6 个月 16 天` | `8 年 6 个月 15 天` | −1 天 |

**根因**：`tools/e2e/tests/d03_calendar.spec.mjs:28`

```js
return { y, m, d: Math.round((now - t2) / 86400000) };   // ← 问题行
```

- `now` 是**带时分秒**的时间戳，`t2` 是当日 **00:00**，所以差值恒为 `整数 + 0.xx 天`。
- 本次执行发生在 **19:01（下午）**，小数部分 0.77 → `Math.round` 进位 +1 天。
- 页面侧（`LoveTime.razor:227`）用的是 `(now - t2).Days`，即 `TimeSpan.Days` 的**向下取整**；《07》LT-26 的预期也写着"`不到 1 天` / `1 天` / `7 天`"（`测试文档-全量测试用例.md:204`，与 §5.4 的 `(0,0,0) → 不到 1 天` 规则一致）。

**判定：产品实现正确，缺陷在测试脚本的期望值算法**（与 2026-11-01 的 NAV-09 同类：断言写错而非功能错）。

**为什么 11-05 那次是绿的**：上午（<12:00）小数部分 <0.5，`round` 与 `floor` 同值 → **假绿**。这条断言的结论会随"几点跑"翻转，属于必须消除的时刻依赖。

## 4. 失败用例修改建议

### 建议 1（必做，1 行）：`d03_calendar.spec.mjs` 改按"日期差"取整

`tests/d03_calendar.spec.mjs:19-29` 的 `ymd()` 末行改为**先把 now 归一到当天 0 点再相减**（推荐写法，彻底去掉时刻依赖）：

```js
function ymd(anchor, now) {
  const a = new Date(anchor.getFullYear(), anchor.getMonth(), anchor.getDate());
  if (now < a) return { y: 0, m: 0, d: 0 };
  let y = now.getFullYear() - a.getFullYear();
  let t = clampAddYears(a, y);
  if (t > now) { y -= 1; t = clampAddYears(a, y); }
  let m = (now.getFullYear() - t.getFullYear()) * 12 + now.getMonth() - t.getMonth();
  let t2 = clampAddMonths(t, m);
  if (t2 > now) { m -= 1; t2 = clampAddMonths(t, m); }
  // ★ 改为"日差"：now 归一到 0 点，与 TimeSpan.Days（向下取整）同义
  const dayStart = new Date(now.getFullYear(), now.getMonth(), now.getDate());
  return { y, m, d: Math.round((dayStart - t2) / 86400000) };
}
```

最小改动版本（只想改一行时）：`Math.round(...)` → `Math.floor((now - t2) / 86400000)`。
两者在非夏令时区结果相同；推荐前者，语义直白、不会被后来者误改回 `round`。

**验证**：

```bash
cd tools/e2e
npx playwright test tests/d03_calendar.spec.mjs          # 期望 6/6 绿
# 时刻依赖性自检：上午跑一次、下午再跑一次，结果必须一致
```

改后 3 条应全绿：今天→`不到 1 天`、昨天→`1 天`、7 天前→`7 天`、闰日→`6 年 8 个月 9 天`、月末→`3 年 9 个月 6 天`、内置日→`8 年 6 个月 15 天`（与本站当前日期相关，按 `ymd` 反算为准）。

**顺带建议**：在该 spec 顶部加一行注释——"天数一律 `floor`／日差取整，禁止 `round`；用 `round` 会在上午跑出假绿、下午跑出必红"。

### 建议 2（建议做）：`NF-01` 的错误详情要能自证

上一轮（18:30）NF-01 失败，本轮（19:01）通过。为定位，我按测试同样的操作序列在 Firefox 下循环复现 6 轮，**复现 2 次（≈33%）**，捕获到固定文本：

```
PAGEERROR: No interop methods are registered for renderer 1
    at blazor.server.js:1:13739
```

- 触发页面：`/game_2048` 载入阶段（`page.goto` 序列）；
- 同期所有 DOM 断言（木鱼 `次数: 1`、2048 `分数：4`、Tetris `["1","0"]`）**全部正常** → **功能无影响**，属渲染器/电路拆除与切换窗口的 interop 竞态；
- 现 `check()` 的 detail 只打印 `errs.length`，失败后无法回溯是哪条异常 → **建议把前 3 条异常文本带进 detail**：

```js
`...；JS 异常=${errs.length}${errs.length ? '：' + errs.slice(0, 3).join(' | ') : ''}`
```

并在断言上加白名单（只放行这一类已知竞态，其它异常仍判红）：

```js
const IGNORE = /No interop methods are registered for renderer/;
const real = errs.filter(e => !IGNORE.test(e));
... && real.length === 0
```

### 建议 3（可选，治本）：消除 `DisposeAsync` 里的 interop 竞态

`Pages/MyPage/Game_2048.razor:445`（与 `Tetris.razor:1091`）的 `DisposeAsync` 会调用 `keyModule.InvokeVoidAsync("unregister", …)`；页面拆除时渲染器可能已注销，服务端这一发就会落到"没有 interop 方法的 renderer"上。

- **Tetris 的 `DisposeAsync` 缺 `catch (JSException)`**（只有 `JSDisconnectedException` / `ObjectDisposedException`），建议补齐；2048 侧同样补一条，避免出现未观察异常；
- 更彻底：把 `unregister` 从销毁路径移出（改由 `NavigationManager.LocationChanged` 在 SPA 切页前主动清理），销毁路径只做 `keyRef?.Dispose()`；
- 若判定"无害且不值得改"，则在《07》NF-01 备注登记为"已知偶发（Firefox，约 1/3），不影响功能"，并采用建议 2 的白名单。

### 建议 4（与失败无关，但本轮暴露）：`/tetris` 没有 `<h1>`

NF-01 的日志恒显示"俄罗斯方块:**空**"，实测 `document.querySelector('h1')` 为 `null`（其余 4 页都有 `h1`；该页只有 `<PageTitle>俄罗斯方块</PageTitle>`）。

- 若希望标题层级统一 / 便于无障碍与自动化判活：在 `Tetris.razor` 补 `<h1>俄罗斯方块</h1>`；
- 若是有意不带大标题：把 NF-01 的页内判活从 `h1` 改成 `.game-canvas` 存在性判断。

### 建议 5（遗留缺陷 D-04，仍建议修）：暂停期间难度仍会上升

TRIS-26 继续 `fixme`。当前实现（`Tetris.razor:995`）只停了下落计时器：

```csharp
private void PauseGame() { isPaused = true; gameTimer?.Stop(); StopSoftDrop(); StateHasChanged(); }
private void ResumeGame() { isPaused = false; gameTimer?.Start(); StateHasChanged(); }
```

最小修复：`PauseGame` 加 `difficultyTimer?.Stop();`、`ResumeGame` 加 `difficultyTimer?.Start();`。
注意副作用：`System.Timers.Timer` 的 `Stop/Start` 会**重置 3 分钟周期**（暂停 3 分钟再继续，要再等 3 分钟才升级）。这符合"暂停冻结"契约，但若产品语义是"累计游玩 3 分钟"，则需记录剩余时间再重启。修完把 TRIS-26 的 `test.fixme` 摘掉即可回归。

## 7. 结论

1. **产品侧本轮未发现新缺陷**：3 条失败全部由测试脚本的 `Math.round` 引起（产品行为与《07》预期、与 `LoveTime.razor` 实现三方一致），改 1 行即可全绿。
2. **D-17（对局进度会话保持）实现质量良好**：新增 7 条专项用例全绿，且与 G2048-27 的改预期协同无误；`test:all` 已把 d17 纳入（默认全量即覆盖）。
3. **唯一需要人工盯的是偶发项 NF-01**（Firefox + `/game_2048`，`No interop methods are registered for renderer 1`，约 1/3 概率），建议先按建议 2 把错误文本落进断言详情 + 白名单，再决定是否治本。
4. **遗留缺陷 D-04 仍未修**（TRIS-26 保持 fixme）；这是账面上唯一的"已知功能缺陷"，两行即可修复。
5. 修改建议全部落地后的预期：**110 条可执行用例全绿**，全量耗时仍在 20 分钟内。
