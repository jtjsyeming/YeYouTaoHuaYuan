## 3. 失败用例与根因

### 3.1 唯一失败：FT-18（P-019）——存档闸放行"上界内伪分"，并污染永久最高分

| 项 | 实测值 |
|---|---|
| 构造存档 | `cells = [2048,1024,512,0…]`，`score = 33790`（`cap = 33792`，即 `cap − 2`） |
| 闸门判定 | `accepted = true`（被当成合法档恢复） |
| 恢复后页面 | `分数：33790` |
| 走一步后 `localStorage` | `bestAfterOneMove = 33790`（**已污染**） |
| 清 `sessionStorage` 后新会话 | `最高分：33790`（**跨会话持久**） |
| 断言 | `fake % 4 = 2`（标准 2048 不可能达到）；`polluted = true` → **FAIL** |

**根因**（`jtjsym/jtjsym/Pages/MyPage/Game_2048.razor:103-118`）：

```csharp
private static bool IsValidArchive(int[] cells, int score)
{
    if (score < 0) return false;
    ...
    return hasTile && score <= scoreCap;   // ← 充分性不足：只证明"不超过理论上界"，未证明"可达"
}
```

三条判据（值域、非空盘、`score ≤ cap`）都是**必要非充分**条件。`cap` 是"把盘面所有块从 2 建起来的总得分"，是**上界**；`33790` 落在这个上界以内，于是被原样恢复。

污染链路是两段式的：
1. **恢复不写 best**（P-003 的修法生效，`Game_2048.razor:467` 已注释掉 `UpdateBestScore()`）→ 但 `Score = 33790` 留在内存；
2. 玩家走**任意一步有效移动** → `AfterMove()`（`:146`）调 `UpdateBestScore()`（`:375`）→ `Score(33798) > BestScore(0)` → `WriteBestAsync()` 写 `localStorage`。

于是 P-003 只是把门槛从"任意伪分"抬高到"上界内伪分"，攻击面缩小但**未关闭**。

**判定：产品缺陷（不是测试脚本错）**。与本轮 e2e 的 0 失败不矛盾——e2e 的 `G2048-41` 只验 `score == cap / cap + 1` 两侧，恰好绕开了"上界内非 4 倍数"这一区间。

## 4. 失败用例修改建议

### 建议 1（必做，1 行，直接关闭 FT-18）：给内容闸补一条**可证的整除判据**

标准 2048 中，合并两个值为 `v` 的块得分 `+2v`；`v` 是 2 的幂且 `v ≥ 2` ⇒ `2v ∈ {4, 8, 16, …}`，**恒为 4 的倍数**；生成新块不计分。故**任何真实对局的总分必为 4 的倍数**。这是一条比 `score ≤ cap` 更强（更接近可达集）且零成本的必要条件。

`Game_2048.razor:105` 之后插入一行：

```csharp
private static bool IsValidArchive(int[] cells, int score)
{
    if (score < 0) return false;
    // ★ P-019：合并得分 = 2v（v ≥ 2 的 2 的幂）⇒ 恒为 4 的倍数，生成新块不计分
    //   故非 4 倍数的分数绝无可能由真实对局产生；比 scoreCap 上界更紧，且 O(1)。
    if ((score & 3) != 0) return false;
    ...
}
```

- `33790 & 3 = 2` → 拒绝 → 清档 → 退化为新局 → `polluted = false` → **FT-18 转 PASS**；
- 对合法档零影响：`cap = 33792`（`33792 & 3 = 0`）、死局档 `24`、边界档 `8` 都是 4 的倍数；
- **不破坏 `G2048-41` 的现有预期**（`score == cap` 放行 / `cap + 1` 拒绝），但会**削弱它的判别力**——见建议 2。

### 建议 2（必做，随建议 1 一起改测试）：`G2048-41` 的边界样本要错开"两个判据"

`tools/e2e/tests/d18_archive_guard.spec.mjs:110-120` 现在用 `9`（`cap + 1`）验上界。加了整除闸后，`9` 会被两条判据同时拒绝——**上界判据坏了这条也不会红**。改成：

```js
// 上界判据专用样本：cap + 4（既越界、又是 4 的倍数）⇒ 只有 scoreCap 能拦住它
await seed(page, archive([4, 4], 12));
checkEq('G2048-41-越界', ... , { score: 0, archive: null }, '比可证上界多 4 分，必须拒绝');

// 整除判据专用样本：cap − 2（在上界内、非 4 倍数）⇒ 只有整除闸能拦住它（P-019 门禁）
await seed(page, archive([4, 4], 6));
checkEq('G2048-41-非4倍数', ... , { score: 0, archive: null }, '上界内但非 4 倍数，绝无可能达到');
```

`[4,4]` 的 `cap = 8`：`12 = 8 + 4`（越界且 4 的倍数）、`6 = 8 − 2`（界内非 4 倍数），两条判据各自被独立验证。

### 建议 3（推荐，清掉**存量**污染）：读取侧也做整除清洗

建议 1 只阻止**新增**污染；已经被写进 `localStorage` 的 `33790` 会永久留着（这正是 FT-18 `bestInFreshSession` 的取值来源）。`best` 同样是分数，**同样必为 4 的倍数**，所以在读 `best` 的地方加同一判据即可一次性清掉历史脏值：

```csharp
// ReadBest / OnInitialized 里解析后：
if (best < 0 || (best & 3) != 0) best = 0;   // 历史伪分（如 P-019 的 33790）就地作废
```

风险可控：真纪录必然是 4 的倍数，不会误杀。若要更保守，可只 `removeItem` 不置 0，下次刷新自然重算。

### 建议 4（治本，按需）：不要相信存档里的分数

P-019 的本质是"用客户端可写的存储承载一个需要防篡改的量"。整除闸只是把攻击面从 100% 压到 25%（4 的倍数、且 ≤ cap 的伪值仍能通过，例如 `33788`）。真正的闭环只有两条路，按投入排序：

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| A. 派生校验 | `score` 不入档，只存 `cells` + 一份**合并摘要**（如每级合并次数向量），恢复时用摘要重算分数并与存档比对 | 中（存档格式 v2 + 兼容旧档） | 想要"零信任"且接受迁移 |
| B. 签名 | 服务端密钥对 `(cells, score)` 做 HMAC，经 JS interop 写入；恢复时校验 | 高（每次落盘多一次往返，影响 P-007 的"看到即已存"不变式） | 有多人排行榜时才有必要 |

个人站点建议停在建议 1+3：**它把"改一行存储就能刷纪录"变成"要精确构造一个 4 的倍数伪分"**，成本收益比最高。若停在 1+3，请在《07》G2048-41 与 §10.1 的 P-019 行显式登记"**降级不闭环**"，避免后续被读成"已修复"。

## 6. 其他遗留与风险项（非失败，但建议排期）

### 6.1 D-04 / TRIS-26：暂停期间难度计时器仍在跑（账面唯一已知功能缺陷）

`Tetris.razor:1008` 的 `PauseGame()` 只 `gameTimer?.Stop()`，漏了 `difficultyTimer`：

```csharp
private void PauseGame() { isPaused = true; gameTimer?.Stop(); StopSoftDrop(); StateHasChanged(); }
private void ResumeGame() { isPaused = false; gameTimer?.Start(); StateHasChanged(); }
```

最小修复：`PauseGame` 加 `difficultyTimer?.Stop();`，`ResumeGame` 加 `difficultyTimer?.Start();`。
注意副作用：`System.Timers.Timer` 的 `Stop/Start` **会重置 3 分钟周期**。若产品语义是"累计游玩 3 分钟"，需记录剩余时间再重启；若语义是"暂停即冻结"，当前两行改法即可，摘掉 `TRIS-26` 的 fixme 后回归。

### 6.2 P-020 / P-021 / P-022：已缓解但现象仍在（**不要**因门禁绿而当作已修）

- **P-020**：零等待 reload 仍会丢最后一步（FT-07 现在只看"DOM 更新后再 reload"这一门禁，`0/8 丢`）；这是 Blazor Server 事件尚未到达服务端的架构边界；
- **P-021**：首帧预渲染必然先画新局（`ServerPrerendered` 读不到 `sessionStorage`），FT-09 已把判据改为"首帧带加载态"，但 `changed=true` 依旧成立；
- **P-022**：恢复窗口内键盘输入被静默丢弃（FT-28 每轮复现，`keysInjected=3` 零生效），且 `.session-tip` 有 20px 纵向抖动。属**可用性现象**，建议在页面加 100ms 级"正在恢复"提示或把键盘注册提前到恢复分支之前。

三者的共同处理建议：在《07》与台账里标注为**设计约束 / 接受残余**，而不是"待修"，否则每轮报告都会重复登记同一条。
