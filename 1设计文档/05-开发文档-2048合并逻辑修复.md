# 开发文档：2048 合并逻辑（Merge）修复

> 版本：v1.0　|　日期：2026-11-01　|　对应文件：`jtjsym/jtjsym/Pages/MyPage/Game_2048.razor`
> 类型：缺陷修复开发文档　|　影响面：2048 页面全部移动操作与计分

---

## 1. 背景与目标

当前 `Game_2048.razor` 的 `Merge()` 方法存在与标准 2048 规则的偏差。该方法是四个方向移动（`MoveLeft/MoveRight/MoveUp/MoveDown`）的公共底层，缺陷会导致：

1. 棋盘出现**不合法的块数**（合并后块没有消失，反而被复制）；
2. **分数虚增**（与实际合并值不符）；
3. 间接影响 `IsGameOver()` 判定的正确性预期（棋盘被"复制"出的块填充，可能提前/延后结束）。

**修复目标**：使移动合并行为完全符合标准 2048 规则，且不改动其他任何机制（生成、结束判定、重玩、UI）。

---

## 2. 现状缺陷分析

### 2.1 现有代码（问题代码）

```csharp
private int[] Merge(int[] line)
{
    var merged = new List<int>();
    var skip = false;

    for (int i = 0; i < line.Length; i++)
    {
        if (line[i] == 0) continue;

        if (!skip && i < line.Length - 1 && line[i] == line[i + 1])
        {
            merged.Add(line[i] * 2);
            Score += line[i] * 2;
            skip = true;
        }
        else
        {
            merged.Add(line[i]);
            skip = false;
        }
    }

    while (merged.Count < GridSize)
    {
        merged.Add(0);
    }

    return merged.ToArray();
}
```

### 2.2 根因

代码意图：`skip = true` 表示"i 与 i+1 已合并，下一步跳过 i+1"。

**实际缺陷**：循环下一轮到达 `i+1` 时，`skip` 只阻止了 `i+1` 与 `i+2` 的*合并判定*（`!skip` 条件失败走 else 分支），但 else 分支仍执行了 `merged.Add(line[i+1])` —— **已消费的第二块被再次放入结果**。

即：`skip` 跳过的是"合并机会"，而不是"元素本身"。合并两个块后，输出了 3 个块。

### 2.3 缺陷推演（逐例 trace）

以向左移动、输入行 `[2, 2, 2, 2]` 为例：

| i | skip 进入时 | line[i] | 分支 | merged 状态 | skip 离开时 |
|---|---|---|---|---|---|
| 0 | false | 2 | 合并（0==1） | [4] | true |
| 1 | true | 2 | else → 加入（重复！） | [4, 2] | false |
| 2 | false | 2 | 合并（2==3） | [4, 2, 4] | true |
| 3 | true | 2 | else → 加入（重复！） | [4, 2, 4, 2] | false |

**结果 `[4, 2, 4, 2]`，标准结果应为 `[4, 4, 0, 0]`。**

更多用例推演（方向：左）：

| 输入 | 现有输出（错） | 标准输出（对） | 缺陷表现 |
|---|---|---|---|
| `[2,2,2,0]` | `[4,2,2,0]` | `[4,2,0,0]` | 第二块被复制 |
| `[2,2,2,2]` | `[4,2,4,2]` | `[4,4,0,0]` | 两对合并全被破坏 |
| `[4,2,2,0]` | `[4,4,2,0]` | `[4,4,0,0]` | 合并出的 4 又"多出"一个 2 |
| `[2,2,0,2]` | `[2,4,2,0]`* | `[4,2,0,0]`* | 压缩与合并顺序错乱（*见 2.4） |
| `[2,0,2,4]` | `[4,4,0,0]`（碰巧对） | `[4,4,0,0]` | 仅此类简单情况结果正确 |

> *注：`[2,2,0,2]` 现有输出实际为 `[4,2,2,0]` 之类的错乱（skip 状态在遇到 0 前后不复位，中间的 0 被 continue 但不影响 skip），总之与标准不符。

### 2.4 附加偏差：压缩与合并的顺序

标准 2048 的语义是**先将所有块朝移动方向压缩靠拢，再对压缩后的序列从移动方向一侧起两两判定合并**。现有代码是边压缩边合并（在同一遍循环里），配合上面的复制缺陷，使"中间有空洞的相同块"场景也会出错。

`MoveRight/MoveUp/MoveDown` 通过 `Reverse()` 复用 `Merge`，方向语义本身是正确的（反转后"左侧优先" = 实际"移动方向一侧优先"），修复 `Merge` 后无需改动这四个方法。

### 2.5 关联观察（不在本次修复范围，另行决策）

- 新块生成概率：`random.Next(1, 3) * 2` 为 2/4 各 50%，标准规则是 **90% 出 2、10% 出 4**；
- 无键盘方向键支持（仅屏幕按钮）；
- tile 无数字区分配色；
- 逻辑内嵌在 .razor 组件中，无法单元测试（本次修复方案中一并给出可测试性建议，见 §7）。

## 3. 标准 2048 合并规则（修复依据）

1. **压缩**：所有非零块朝移动方向靠拢，不留空洞；
2. **合并**：从移动方向一侧开始扫描，相邻两个等值块合并为一个双倍值块；**合并后的新块在本步移动中不能再参与合并**；
3. **每块每步最多参与一次合并**：`[4,2,2]` → `[4,4]`（右侧 2 先合并），合并出的 4 不得再与左侧 4 合并；
4. **等值三连**：`[2,2,2]` → `[4,2]`（靠移动方向的一对先合并）；
5. **计分**：每合并一次，得分加上合并产生的新块值（`[2,2]`→4 得 4 分；`[4,4]`→8 得 8 分）；
6. **移动后**：若棋盘有变化（发生合并或块位移），生成一个新块；若棋盘无变化，不生成新块、不产生任何效果。

> 现有代码未实现第 6 条的"无变化不生成新块"，本次一并纳入修复范围（改动小、属于同一移动流程），见 §4.4。

---

## 4. 修复方案设计

### 4.1 算法设计：压缩 → 成对消费

将 `Merge` 重写为两步式，用索引消费彻底消除 `skip` 标志的状态混乱：

```
输入: line（含 0 的长度为 4 的行/列，已按移动方向对齐）
Step1 压缩: 取出所有非零值，保持相对顺序 → values
Step2 成对消费: i 从 0 起，每次处理一个"组"
    - 若 values[i] == values[i+1] → 输出 values[i]*2，计分，i += 2（两块同时消费，杜绝复制）
    - 否则 → 输出 values[i]，i += 1
Step3 补零: 结果不足 4 位则尾部补 0
输出: 新的行/列
```

由于每轮 `i += 2`，合并对的两个块都从输入中消失，**结构性上不可能出现复制**；成对消费也天然满足"合并后的块不再参与本步合并"（新块直接进入输出，不回看）。

### 4.2 修复后代码（替换 `Game_2048.razor` 中的 `Merge` 方法）

```csharp
private int[] Merge(int[] line)
{
    // Step1: 压缩 —— 取出所有非零块，保持相对顺序
    var values = new List<int>();
    foreach (var v in line)
    {
        if (v != 0) values.Add(v);
    }

    // Step2: 从移动方向一侧起成对消费，等值即合并
    var merged = new List<int>();
    int i = 0;
    while (i < values.Count)
    {
        if (i + 1 < values.Count && values[i] == values[i + 1])
        {
            merged.Add(values[i] * 2);
            Score += values[i] * 2;
            i += 2;   // 两个块同时消费 —— 关键：不复制、不回看
        }
        else
        {
            merged.Add(values[i]);
            i += 1;
        }
    }

    // Step3: 尾部补零
    while (merged.Count < GridSize)
    {
        merged.Add(0);
    }

    return merged.ToArray();
}
```

复杂度：O(n)（n=4），与原实现相同；无额外状态标志，行为可用纯输入输出验证。

| `[2,2,2,0]` | `[4,2,0,0]` | +4 | ✔ |
| `[4,2,2,0]` | `[4,4,0,0]` | +4 | ✔（合并出的 4 不再与左 4 合并） |
| `[2,2,0,2]` | `[4,2,0,0]` | +4 | ✔（先压缩再合并） |
| `[2,0,2,4]` | `[4,4,0,0]` | +4 | ✔ |

### 4.4 同步小改：移动无变化时不生成新块

在 `AfterMove()` 中增加"棋盘是否变化"判断，符合标准规则第 6 条：

```csharp
private bool boardChanged;   // 新增字段

private void AfterMove(int[,] boardBefore)
{
    bool changed = IsBoardChanged(boardBefore, board);
    if (changed)
    {
        AddRandomTile();
        if (IsGameOver())
        {
            isGameOver = true;
        }
    }
    StateHasChanged();
}

private static bool IsBoardChanged(int[,] before, int[,] after)
{
    for (int row = 0; row < GridSize; row++)
        for (int col = 0; col < GridSize; col++)
            if (before[row, col] != after[row, col])
                return true;
    return false;
}
```

调用侧改动（四个移动方法统一模式）：

```csharp
private void MoveLeft()
{
    var before = (int[,])board.Clone();          // 记录移动前棋盘
    for (int row = 0; row < GridSize; row++)
    {
        SetRow(row, Merge(GetRow(row)));
    }
    AfterMove(before);
}
// MoveRight / MoveUp / MoveDown 同理：首行加 Clone，末行传 before
```

> `board` 为 `int[4,4]`，`Clone()` 成本可忽略。若希望改动最小，本节为**可选项**，仅实施 §4.2 也能修复主要缺陷；但建议一并实施以获得完整的标准行为。
