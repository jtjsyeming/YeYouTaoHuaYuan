## 0. 本次修订摘要

v1.0 的**技术方向（CSS 变量 + `min()`，无 JS）是对的**，但根因定位、尺寸预算、断点选择三处都有实质偏差，按原方案实施后 §5 的 T3/T7 两条关键用例**会失败**。

## 1. 检视结论：真正的根因不是格子尺寸

v1.0 §2.1 的推断是"375px 下 300px 网格 + 110px 面板 ≈ 420px > 375px"。方向对，但漏了最关键的一层——**`.top-area` 只给 80% 宽**。

```css
.top-area { display: flex; width: 80%; max-width: 600px; gap: 10px; }
.game-area { flex: 3; }          /* 内含 300px 画布 */
.side-panel { flex: 1; min-width: 110px; }
```

`.game-canvas` 宽 = 10×30 + 4（边框）= **304px**，`min-content` 撑住 `.game-area` 不可再收缩，所以横排的硬性下限是 `304 + 10 + 110 = 424px`。

而 `.top-area` 的实际宽度是 `min(0.8 × (可用宽), 600px)`：

| 视口 W | 侧栏 | 内容宽（扣 `px-4`） | 容器内宽（扣 padding 20） | `.top-area` 宽 | 需 424px | 结论 |
|---|---|---|---|---|---|---|
| 1440 | 250 | 1134 | 1114 | 600（max 封顶） | ✔ | 正常 |
| 1024 | 250 | 718 | 698 | 558 | ✔ | 正常 |
| 900 | 250 | 594 | 574 | 459 | ✔ | 正常 |
| **857** | 250 | 551 | 531 | **425** | ✔ 临界 | 临界点 |
| 768 | 250 | 462 | 442 | 354 | ✘ 差 70 | **溢出** |
| **641** | 250 | 305 | 285 | 228 | ✘ 差 196 | **溢出（断崖）** |
| 640 | 无 | 592 | 572 | 458 | ✔ | 正常 |
| **600** | 无 | 552 | 532 | 426 | ✔ 临界 | 临界 |
| 500 | 无 | 452 | 432 | 346 | ✘ 差 78 | **溢出** |
| 375 | 无 | 327 | 307 | 246 | ✘ 差 178 | **溢出** |
| 320 | 无 | 272 | 252 | 202 | ✘ 差 222 | **严重溢出** |

### 1.1 两个必须修正的认知

**① 溢出区间是"两段"，不是"小屏一段"**

- `W < 857px`：有侧栏（250px）时横排放不下 → **641~856px 这段（笔记本窄窗、平板竖屏）现在就是坏的**；
- `W < 492px`：无侧栏时横排放不下 → 这才是"手机段"。

**② 641px 处存在断崖**

`MainLayout.razor.css` 在 `min-width: 641px` 突然插入 250px 侧栏 + 32/24px 内边距，可用宽度从 **592px 骤降到 305px**。所以 **640px 正常、641px 严重溢出**——这是本项目移动端适配最反直觉的一点，v1.0 完全没考虑。

### 1.2 可用宽度公式（实测盒模型）

```
W < 641px（无侧栏）：
  可用宽 I = W − 48（article 的 Bootstrap px-4：24×2）
                − 20（.tetris-container padding:10px×2）
  → 格子约束：10c + 4（.game-canvas border:2px×2） ≤ I
    c ≤ (W − 72) / 10

W ≥ 641px（有侧栏）：
  I = W − 250（sidebar） − 32 − 24（article padding-left/right !important） − 20
    = W − 326
```

> W < 641px 时 `.page` 是 `flex-direction: column`，侧栏在顶部；`article` 只受 Bootstrap `px-4` 影响（24px 两侧）。
> 另需为**竖向滚动条**（约 15px）与设备像素取整留余量，实际建议按 `W − 78` 计算。

## 2. 方案设计

### 2.1 三层修复（缺任何一层都不完整）

```
第 1 层：放开 .top-area 宽度      → 解决 641~856px 的溢出（横排仍可用）
第 2 层：窄屏改纵向堆叠（≤520px） → 解决手机段"网格 + 侧栏横排"必然放不下
第 3 层：格子尺寸随视口收缩       → 解决 ≤372px 时 304px 网格仍比可用宽
（附带）第 4 层：按钮区在 ≤340px 缩一档 → 解决 291px 按钮组溢出
```

v1.0 只做了第 3 层 + 半个第 2 层（断点太窄且没放开 `.top-area`），所以只会在 480px 以下的真机"看起来好一点"，而 500~856px 的窗口依然是坏的。

### 2.2 第 1、2 层：容器宽度与堆叠

```css
/* 新增——放在 Tetris.razor 的 <style> 末尾 */

/* L1：641~900px 放开 80% 限制，横排恢复可用（桌面 ≥901px 保持原样） */
@media (max-width: 900px) {
    .top-area {
        width: 100%;
    }
}

/* L2：手机段纵向堆叠。520px 而非 480px —— 480~492px 横排会差 12px 仍溢出 */
@media (max-width: 520px) {
    .top-area {
        width: 100%;
        flex-direction: column;
        align-items: center;
        gap: 8px;
    }

    .game-area {
        flex: none;          /* 竖排时 flex:3 无意义，且会干扰高度计算 */
        width: auto;
    }

    .side-panel {
        flex: none;
        box-sizing: border-box;                       /* 关键：否则外宽多 28px */
        width: calc(var(--cell-size) * 10 + 4px);     /* +4px 对齐画布 4px 边框 */
        max-width: 100%;
        min-width: 0;
    }
}
```

- 断点选择依据：横排硬性下限 424px，无侧栏时 `I = W − 68` → `W ≥ 492px` 才能横排，取 520px 留余量；
- 900px 的上界依据：`W = 857px` 时横排刚好临界，900px 覆盖到安全侧；
- 桌面 ≥901px：`width: 80%` 保持不变，**视觉零变化**（满足硬性验收项）。

### 2.3 第 3 层：格子尺寸（修正预算）

```css
.tetris-container {
    /* 修正：72px = px-4(48) + 容器 padding(20) + 画布边框(4)；再留 6px 给竖滚动条与取整 */
    --cell-size: min(30px, calc((100vw - 78px) / 10));
}
```

| 视口 | 命中值 | 网格宽（含画布边框） | 可用宽 I（W−68） | 结论 |
|---|---|---|---|---|
| ≥378px | 30px | 304 | ≥310 | 不缩放（与现状完全一致） |
| 375px | 29.7px | 301 | 307 | 几乎不可察觉的微缩 |
| 360px | 28.2px | 286 | 292 | 不溢出 |
| 320px | 24.2px | 246 | 252 | 不溢出 |
| 280px | 20.2px | 206 | 212 | 不溢出 |

> 30px 的临界点是 `30×10 + 78 = 378px`：378px 以上完全不变形（严格满足"桌面零变化"），375px 起才开始微缩。

> **对比 v1.0**：同样 320px，v1.0 得 28.8px → 网格 292px > 可用 252px → 仍溢出 40px（T7 会失败）。

格子与预览块：

```css
.grid-cell, .piece-cell, .piece-empty {
    width: var(--cell-size);
    height: var(--cell-size);
    box-sizing: border-box;   /* 原有 .grid-cell/.piece-cell 已具备，.piece-empty 补上 */
}

.side-panel { --preview-size: min(18px, calc(var(--cell-size) * 0.6)); }
.preview-cell { width: var(--preview-size); height: var(--preview-size); }
```

### 2.4 overlay 内联样式去硬编码（v1.0 最有价值的一条，保留）

```razor
@* 改前 *@
<div class="current-piece-overlay" style="top: @(y * 30)px; left: @(x * 30)px;">
@* 改后 *@
<div class="current-piece-overlay" style="top: calc(var(--cell-size) * @(y)); left: calc(var(--cell-size) * @(x));">
```

- `--cell-size` 定义在 `.tetris-container`，overlay 是其孙元素，`var()` 正常继承；
- 网格与 overlay 使用**同一套小数坐标**（都来自 `--cell-size`），布局层不会累积错位，风险仅为 ≤1 设备像素的发丝缝（见 §5）；
- C# 侧 `x`/`y` 仍是整数格子坐标，**游戏逻辑零改动**。

### 2.5 第 4 层：按钮区（v1.0 漏项）

现宽 `旋转 90 + gap 20 + (55×3 + 8×2)` = **291px**；320px 视口可用仅 252px。

```css
@media (max-width: 400px) {
    .direction-pad { gap: 12px; }
    .dir-buttons { gap: 6px; }
    .rotate-btn { width: 74px; height: 46px; font-size: 16px; }
    .direction-btn { width: 46px; height: 46px; font-size: 20px; }
}
/* 新宽 = 74 + 12 + (46×3 + 6×2) = 236px ≤ 252px */
```

### 2.6 2048（如实说明收益）

按真实预算（`px-4` 48 + 容器 padding 40 + 边框 2 + gap 15 ≈ 105px，取 120px 保守）计算：

| 视口 | `(W−120)/4` | tile | 与现状 |
|---|---|---|---|
| ≥320px | ≥50 | 50px | **完全一致**（字号 `50×0.4 = 20px` 也一致） |
| 300px | 45px | 45px | 才开始生效 |

结论：**2048 部分在主流手机宽度下零变化，属于防御性改动**（保护 <305px 与未来调大 tile 的情况）。两个选择：

- **推荐**：保留（改动 3 行、无风险），但把 §1 目标改写成"为 <305px 提供防线，主流机型无视觉变化"；
- 若追求"零无操作 diff"，可把 2048 移出本次范围，只做 Tetris。

```css
.game-container { --tile-size: min(50px, calc((100vw - 120px) / 4)); }
.tile {
    width: var(--tile-size);
    height: var(--tile-size);
    box-sizing: border-box;                        /* 现有无 box-sizing，补上以免 1px 边框叠加 */
    font-size: calc(var(--tile-size) * 0.4);
}
```

> 4 位数（1024/2048）：tile 50px 时字号 20px，"2048" 约 44px，块内可用宽 48px，仍在安全区；tile 45px 时字号 18px，约 40px < 43px，同样安全。

```js
// DevTools Console 执行（切换到目标视口后）
const doc = document.documentElement;
console.log('横向溢出:', doc.scrollWidth > doc.clientWidth, doc.scrollWidth, doc.clientWidth);

const canvas = document.querySelector('.game-canvas');
const ov = document.querySelector('.current-piece-overlay');
console.log('画布宽:', canvas.getBoundingClientRect().width,
            'overlay 左上:', ov.style.top, ov.style.left);
```

`doc.scrollWidth > doc.clientWidth` 必须为 `false`（无横向滚动条）。

## 6. 风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| 子像素取整导致发丝缝 | 视觉瑕疵 | 网格与 overlay 共用同一小数坐标，**布局层不会累积错位**，仅每格边界可能 ≤1 设备像素误差；若实测明显，改分段整数档位（§7-2） |
| `100vw` 含竖向滚动条宽 | 公式高估可用宽 → 375px 时反而溢出 | 预算已从 72px 提到 78px 留 6px 余量；T15 专项验证 |
| 900px 断点误伤平板横屏 | 平板横屏 `.top-area` 变 100%（面板与网格间距变化） | 仅宽度变化，不改变排布；如需更精确可改 `(max-width: 900px) and (min-width: 521px)` |
| `var()` 在内联 style 中的兼容性 | 老浏览器 overlay 错位 | Blazor Server 只支持现代浏览器；iOS Safari 9.3+ 全支持 |
| 变量拼写/作用域错误 | overlay 飞出棋盘 | 变量定义在 `.tetris-container` 根，继承链明确；T7/T8 验证 |
| 2048 改动收益近零 | 无意义 diff | 已如实说明（§2.6），可移出本次范围 |
