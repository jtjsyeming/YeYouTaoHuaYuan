> 合并理由：两条同在 `LoveTime.razor`，都是"**状态变了但渲染没跟着全量刷新**"的一致性问题，改动集中且互不冲突

> v2.0 据此把验收换成**相位对齐的确定性判据**（未修复 3/3 必红、修复后 3/3 必绿，本轮已实测），并把 P-014 的"验证"如实降级为"结构可复核 + 相邻性质有守"。

## 2. 修复方案

### 2.1 P-010：落点就是两处，形态只能是 `RefreshAll()`

改动只有两行：

```csharp
        anchorDates[type] = selectedDate;
        RefreshAll();     // 三行同源重算：只刷一行会让另两行停在上一 tick（[34,33,33]）
        // 事件回调结束后 Blazor 自动重渲染，无需 StateHasChanged()
```

```csharp
        anchorDates[type] = timePoints[type];
        validationMessage = null;
        RefreshAll();
```

**为什么不是"连调三次 `Render`"**：也能对齐，但把"三行"这个知识散到了两个调用点；`RefreshAll` 本来就是它的唯一所有者，事件回调和 ticker 复用同一段代码，后续加第四条时间线只需改一处。

**为什么不是"把 ticker 的 `now` 缓存起来给事件回调用"**：那样三行确实一致，但会**一致地落后**——用户点按钮后看到的还是上一次 tick 的秒数，比"两行落后一秒"更难察觉。本次两条问题的共同主题是"同源"，不是"看起来一样"。

**为什么同帧**：`Render` 只改 `elapsedTimes[type].ElapsedTime / CalendarText` 两个字符串，三行的更新在同一次渲染批次里提交，浏览器侧不会出现"改了一半"的中间态（这也是 §4.2 判据成立的前提）。

### 2.2 P-010（防复发）：`Render` 的 `now` 必须变成必传参数

改完 §2.1 后，`Render` 的调用点只剩 `RefreshAll` 一处。此时的 `DateTime? now = null` 有两个毛病：

- `var n = now ?? DateTime.Now;` 永不执行 —— 死代码；
- 它是一个**降级入口**：将来任何人加一个"只刷一行"的调用点，写 `Render(anchor, type)` 就能编过，P-010 原样复发，而且编译器和评审都看不出来。

所以顺手收口（3 行）：

```csharp
    private void Render(DateTime anchor, string type, DateTime now)
    {
        var elapsed = now - anchor;
```

```csharp
        // 日历换算用未 clamp 的 (anchor, now)：anchor 恒为零点、now 含时分秒，now < anchor 时方法内兜底
        var (y, m, d) = CalendarElapsed(anchor, now);
```

即：删掉 `DateTime? now = null`、删掉 `var n = now ?? DateTime.Now;`，把方法体里两处 `n`/`n - anchor` 改成 `now`。

> 这一步**不是**为了 P-010 本身（两行改动已经修好），而是把"取时点唯一"从约定变成类型约束 —— 与《15》把 `ElapsedTimeInfo` 的三个死属性删掉同一种洁癖：留下"算了没人读"或"写了永不执行"的东西，下一次就会被人用错。

### 2.3 P-014：`readonly` 是硬阻塞，口径改为"惰性构建 + 短路"

v1.0 的形态是把 `years` 重新赋值，但它是 `readonly`：

```csharp
    private readonly List<string> years =                              // ← L108
        Enumerable.Range(1950, DateTime.Now.Year - 1949).Select(y => y.ToString()).ToList();
```

原样贴入 v1.0 §2.2 的代码，实测报错：

```
LoveTime.razor(201,9): error CS0191: 无法分配到只读字段(除非在定义了该字段的类型的构造函数或 init-only 资源库中，或者在变量初始值设定项中)
```

两种改法（都能编过）：

| 改法 | 代价 | 结论 |
|---|---|---|
| A. 去掉 `readonly`，保留字段初始值 | 1 个字 | 可行，但 `years` 与 `yearsBuiltFor` 是**两次独立的 `DateTime.Now`** 初始化，跨年边界会出现"列表是旧年、闸门是新年"→ 早退 → P-014 复现（概率极低但确实是同一个 bug 的残余） |
| **B. `years = new()` + `yearsBuiltFor = 0`** | 1 次极小的首次分配 | **采用**。`yearsBuiltFor = 0` 保证首次 `RefreshAll` 必建，构建与闸门**天然同步**，不存在对不齐的可能 |

采用 B 后的字段声明：

```csharp
    private List<string> years = new();     // P-014：由 EnsureYearsFresh 构建（跨年自愈），不再一次性生成
    private int yearsBuiltFor;              // 0 → 首次 RefreshAll 必建一次，避免"字段初始化跨年对不齐"
    private readonly List<string> months =
```

**`years` 初值为空安全吗？** 安全。首次构建发生在 `OnInitialized → RefreshAll()`（L127），而渲染在其后才开始，markup 里的 `@foreach (var y in years)` 不会看到空列表。实测 LT-05（年份下拉 77 项、首项 `1950`、末项当前年、默认选中 `1950`）通过。

### 2.4 P-014：为什么短路不能省，也不能用"每秒重建"

```csharp
    private void EnsureYearsFresh(int currentYear)
    {
        if (currentYear == yearsBuiltFor) return;      // ← 这一行是必需的，不是优化
        yearsBuiltFor = currentYear;
        years = Enumerable.Range(1950, currentYear - 1949).Select(v => v.ToString()).ToList();
    }
```

不带短路也能"跑得动"，但等于把"重建 77 个字符串 + 让 Blazor 每秒 diff 77 个 `<FluentOption>`"塞进每秒热路径。**判据不是性能，是副作用面**：`fluent-select` 的 `value` 由 `@bind-Value` 回写，把"列表重建"这种可能触发回写的动作放大到每秒一次，是给自己开一个不必要的风险面（实测当前 Blazor 的 diff 在"前缀相同、末尾追加"时不会重置 `value`，见 §5-6；但把一个不需要的动作放进每秒热路径，收益是零）。

**为什么不原地 `years.Add(...)`**：也行（`readonly` 甚至都不用动），但需要处理"跨了两年"的循环，且"列表内容变了但引用没变"对 Blazor 的 diff 是更隐晦的语义。引用替换更直白：**只有年份真的变了才换引用**，diff 结果就是"末尾追加一项"。

**需要给 `FluentSelect` 加 `@key` 吗？不需要（实测）**：往 `years` 末尾追加一项后，`fluent-select` 的 `value` 保持为已选值（实测 `1950`），追加出来的 `2026` 也能正常选中。日期下拉的 `@key`（L48）是因为**选项集合会整体变化**（28/29/30/31 天互换），年份列表只会在末尾单向追加，性质不同。

## 4. 测试计划

### 4.1 先看数据：为什么 v1.0 的验收不成立

**（一）FT-11 不是门禁。** `Test/functiontest.mjs` 的运行器：

```js
const kind = r.kind || (r.pass ? 'pass' : 'fail');
...
pass: results.filter(r => r.kind === 'pass').length,
fail: results.filter(r => r.kind === 'fail' || r.kind === 'error').length,
observe: results.filter(r => r.kind === 'observe').length,
```

FT-11 返回 `kind: 'observe'` → 只进 `observe` 桶；`fail` 不统计它；全脚本没有 `process.exit`/`exitCode`，**退出码恒 0**。所以"FT-11 复跑转 PASS"只能靠人眼看输出，红绿都不拦任何东西。

**（二）就算按人眼看，它一半会漏。** 本轮按 FT-11 原样的判据（连续 12 次点"恢复默认"、每次点完立刻采三行秒数、间隔 110ms）跑了 4 次**独立加载**，都是**同一份未修复代码**：

| 加载 | ticker 相位 φ（tick 相对整秒的偏移） | 12 次采样中不一致次数 |
|---|---|---|
| 1 | 115 ms | **0** |
| 2 | 173 ms | **0** |
| 3 | 397 ms | 2 |
| 4 | 705 ms | 4 |

**两次"干净通过"，而 bug 就在那里。** 原因不是随机噪声，是结构性的：

- `PeriodicTimer` 从 `OnAfterRender(firstRender)` 起算，相位 φ 由"页面开始交互的那一瞬"决定，**每次加载都不同**；
- 设 tick 在 `k+φ` 触发，它读到的是第 `k` 秒；下一次 tick 在 `k+1000+φ`；
- 点击落在 `[k+φ, k+1000)` → 新旧同秒，**看不出问题**；落在 `[k+1000, k+1000+φ)` → 被点行走新秒、另两行还是 `k`，**必然不一致**；
- 所以**能观测的窗口宽度恰好等于 φ**。φ=115ms 时 12 次采样期望命中 1.4 次、实测 0 次；φ=705ms 时才是"大概率命中"。

> 实测命中数系统性低于"φ/1000×12"（φ=705 时模型给 8.5、实测 4）：12 次点击按固定 110ms 间隔排，叠加每次 `click()` + `evaluate()` 的 CDP 往返后，相位被量化到约 170~200ms 一格，落进窗口的样本数有限 —— 也就是说**原判据的实际命中率比理论值还低**。

> 这也解释了报告里写"12 次采样 4 次不一致"、而我今天第一次复现是 6 次——不是环境抖动，是每次加载的 φ 不同。
>
> 顺带：v1.0 §4 #1 要求"12 次全部一致"作为**验收**，实际是"12 次里有 0 次不一致" → 一个 φ 很小的加载会让回归直接通过。**这条判据不能用作门禁。**

### 4.2 相位对齐：把"大概率"换成"必然"

把上面那张表的逻辑倒过来用，就能构造确定性命中：

1. 观察一次秒刷（对首行 `div.timer` 挂 `MutationObserver`），记下文本变化的 `Date.now()`，其 `% 1000` 即 φ；
2. 若 φ < 250ms（窗口太窄，容不下点击+采样的往返），**重新加载换一个相位**重试（φ 均匀分布，实测 3/3 首测即 ≥ 250ms）；
3. 等到"下一个整秒边界 + 40ms"再点击 —— 此刻上一次 tick 显示的是**上一秒**，下一次 tick 还要等 φ-40ms；
4. 点击后在 `[边界+40ms, 边界+φ-40ms)` 之间**反复采样**（若不一致会一直保持到下一次 tick，所以轮询比单点更稳）。

未修复时的签名非常干净：**被点那一行是 `k`，另两行是 `k-1`**。

```js
// P-010 / P-014：爱情计时器事件回调后的渲染一致性
// 核心手法：相位对齐。ticker 每秒一次，但相位 φ（tick 相对整秒的偏移）由"页面开始交互的那一瞬"决定，
// 每次加载都不同；能观测到 P-010 的窗口宽度恰好等于 φ。故先量 φ、φ 太小就重新加载换相位，
// 再在"整秒边界之后、下一次 tick 之前"点击 —— 这样"被点行走新秒、另两行还在旧秒"是必然事件，不是概率事件。
import { test } from '@playwright/test';
import { check, open, pickSelect, readLoveTime, sleep } from './helpers.mjs';

const MIN_PHI = 250;   // 低于这个值，点击+采样的往返会吃掉整个窗口

/** 观察一次秒刷，返回该次 tick 时刻的 Date.now()（毫秒）；5s 内没有变化返回 null */
const observeTick = page =>
  page.evaluate(
    () =>
      new Promise(resolve => {
        const el = document.querySelectorAll('div.timer')[0];
        const obs = new MutationObserver(() => {
          obs.disconnect();
          resolve(Date.now());
        });
        obs.observe(el, { childList: true, characterData: true, subtree: true });
        setTimeout(() => {
          obs.disconnect();
          resolve(null);
        }, 5000);
      }),
  );

/** 取一次 φ ≥ MIN_PHI 的加载（每次 goto 都是新电路、新相位） */
async function loadWithGoodPhase(page) {
  for (let i = 0; i < 6; i++) {
    await open(page, '/loveTime', 2200);
    const t = await observeTick(page);
    if (t !== null && t % 1000 >= MIN_PHI) return t % 1000;
  }
  return null;
}

const readSecs = page =>
  page.evaluate(() =>
    [...document.querySelectorAll('div.timer')].map(t => {
      const m = /(\d+)\s*秒/.exec(t.textContent);
      return m ? +m[1] : null;
    }),
  );

test('LT-31 事件回调：三行秒数必须同步进入新秒（相位对齐，确定性）', async ({ page }) => {
  const phi = await loadWithGoodPhase(page);
  check('LT-31-相位', phi !== null, `ticker 相位 φ=${phi}ms（需 ≥ ${MIN_PHI}，6 次加载仍未取到即判红）`);
  if (phi === null) return;

  // 等到"下一个整秒边界 + 40ms"
  const nowMs = await page.evaluate(() => Date.now());
  const boundary = Math.floor(nowMs / 1000) * 1000 + 1000;
  await sleep(Math.max(0, boundary + 40 - nowMs));

  // 点击（用 DOM click 而非 locator.click：省掉 hit-test，时序更准）
  await page.evaluate(() => document.querySelectorAll('.love-reset-bar fluent-button')[0].click());

  // 在下一次 tick（boundary+φ）之前反复采样：不一致会一直保持到那次 tick，轮询比单点稳
  const deadline = boundary + phi - 40;
  let last = null;
  let bad = null;
  while (Date.now() < deadline) {
    last = await readSecs(page);
    if (new Set(last).size > 1) {
      bad = last;
      break;
    }
    await sleep(20);
  }

  check(
    'LT-31',
    bad === null,
    `φ=${phi}ms，整秒边界后 40ms 点击 → 三行秒数 ${(bad ?? last ?? []).join('/')}` +
      `（未修复时必为 "k/k-1/k-1"，k 为被点行）`,
  );
});

test('LT-32 秒级重渲染不破坏年份/日期下拉（P-014 相邻性质）', async ({ page }) => {
  await open(page, '/loveTime', 2000);
  await pickSelect(page, 0, '2020');
  await pickSelect(page, 1, '2');
  await pickSelect(page, 2, '29');   // 2020-02 有 29 天
  const before = await readLoveTime(page);
  const expectYears = new Date().getFullYear() - 1950 + 1;

  await sleep(3200);                 // 让 RefreshAll/EnsureYearsFresh 跑满 3 个 tick
  const after = await readLoveTime(page);

  check(
    'LT-32-年份',
    after.yearCount === expectYears && after.y === '2020',
    `年份选项 ${after.yearCount} 项（期望 ${expectYears}），已选=${after.y}`,
  );
  check(
    'LT-32-日期',
    after.dayOptions.length === 29 && after.d === '29',
    `日期选项 ${after.dayOptions.length} 项（2020-02 应为 29），已选=${after.d}`,
  );
  check(
    'LT-32-稳定',
    before.y === after.y && before.m === after.m && before.d === after.d,
    `3 个 tick 前后选择应不变：${before.y}-${before.m}-${before.d} → ${after.y}-${after.m}-${after.d}`,
  );
});
```

**LT-32 只能做到这一步，必须说清**：

- 它守的是"每秒跑一次年份检查"**没有副作用**（列表项数、已选值、日期选项集合都不被扰动）——这正是"每次重建而不短路"这类错误实现的暴露点；
- 它**不能**证明"跨年那一秒会自愈"。服务端 `DateTime.Now` 无法伪造（Playwright 的 `clock` 只改浏览器侧时间），跨年切换没有任何端到端手段。台账里 C-20 的关闭依据必须这么写，不能写"已验证"。

### 4.4 `Test/functiontest.mjs` FT-11 判据改写（**必须显式登记，不能悄悄改**）

现状与问题：

| 项 | 现状 | 问题 |
|---|---|---|
| 判据 | 12 次连点 + 单点采样 | 命中率 = φ/1000，实测 4 次加载有 2 次 0 命中 |
| `kind` | `'observe'` | 只进 `observe` 桶，永远不算失败；脚本无 `process.exit`，退出码恒 0 |
| 采样时机 | `click()` 后立刻 `evaluate` | 若服务端渲染尚未完成，读到的是"三行全旧"→ 又一次漏检（需轮询，不能单点） |

改写方案（`kind` 由 `'observe'` 升级为 `'pass'`，判据换成相位对齐）：

```js
ft('FT-11', 'D-03', '自选/恢复按钮后三行秒数的瞬时一致性（相位对齐）', async browser => {
  const { ctx, page, errs } = await fresh(browser);
  const MIN_PHI = 250;
  const secs = () => page.evaluate(() => [...document.querySelectorAll('div.timer')].map(t => {
    const m = /(\d+)\s*秒/.exec(t.textContent); return m ? +m[1] : null;
  }));

  // ① 取一次 φ ≥ MIN_PHI 的加载
  let phi = null;
  for (let i = 0; i < 6; i++) {
    await open(page, '/loveTime', 2200);
    const t = await page.evaluate(() => new Promise(resolve => {
      const el = document.querySelectorAll('div.timer')[0];
      const obs = new MutationObserver(() => { obs.disconnect(); resolve(Date.now()); });
      obs.observe(el, { childList: true, characterData: true, subtree: true });
      setTimeout(() => { obs.disconnect(); resolve(null); }, 5000);
    }));
    if (t !== null && t % 1000 >= MIN_PHI) { phi = t % 1000; break; }
  }
  if (phi === null) {
    await ctx.close();
    return { pass: false, expect: '三行秒数必须同时进入新秒', actual: { error: '6 次加载均未取到 φ ≥ 250ms 的相位' }, kind: 'pass' };
  }

  // ② 等到"下一个整秒边界 + 40ms"，点击，并在下一次 tick 之前轮询
  const nowMs = await page.evaluate(() => Date.now());
  const boundary = Math.floor(nowMs / 1000) * 1000 + 1000;
  await sleep(Math.max(0, boundary + 40 - nowMs));
  await page.evaluate(() => document.querySelectorAll('.love-reset-bar fluent-button')[0].click());

  const deadline = boundary + phi - 40;
  let last = null, bad = null;
  while (Date.now() < deadline) {
    last = await secs();
    if (new Set(last).size > 1) { bad = last; break; }
    await sleep(20);
  }
  await ctx.close();
  return {
    pass: bad === null,
    expect: '整秒边界后点击：三行秒数必须同时进入新秒（未修复时被点行为 k、另两行为 k-1）',
    actual: { phi, mismatch: bad, lastSeen: last, errors: errs.slice(0, 3) },
    kind: 'pass',
  };
});
```

> 升级 `kind` 的后果要写进执行记录：**FT-11 从此会真的把整轮判为 fail**。这是有意的——它现在有确定性命中能力；保留 `'observe'` 等于保留一个永远不报警的观察项。
> 若实施时不想动 functiontest（例如担心影响既有 FT 统计口径），最低要求是：**把 v1.0 §4 里"FT-11 转 PASS"这句验收删掉**，只留 LT-31 作为门禁，并在台账 C-19 的关闭依据里写明"FT-11 为观察项，非门禁"。

## 5. 残余边界与误判风险（如实登记）

| # | 边界 | 影响 | 处置 |
|---|---|---|---|
| 1 | 相位对齐依赖 φ ≥ 250ms | φ 太小则窗口只有几十毫秒，点击+采样往返吃掉窗口 → 该次判据无效 | 最多重新加载 6 次换相位；理论失效概率 ≈ 0.25⁶ ≈ 0.02%。仍失败时 LT-31-相位 单独判红（不会静默通过） |
| 2 | 跨年自愈**无端到端验证** | C-20 只有"结构可复核 + LT-32 相邻性质" | 台账关闭依据照实写；不要把 LT-32 说成"验证了跨年" |
| 3 | 系统时钟被 NTP 大步跳变 | 整秒边界算错，点击可能落在窗口外 | 开发机常态下不会发生；若执行记录里出现"边界后点击仍一致"，先查时钟同步 |
| 4 | 与 D-08（后台标签仍在每秒推帧）的关系 | P-014 的自愈依赖 ticker 持续运行 | 若将来为 D-08 加"后台暂停 ticker"，回到前台后第一次 `RefreshAll` 会立刻补建年份列表 —— **仍是自愈，只是延迟到用户回来**，不冲突；但实施 D-08 时必须回归 LT-32 |
| 5 | `EnsureYearsFresh` 挂在 `RefreshAll` 里 | 若将来把 ticker 换成"按需刷新"，年份自愈会跟着失效 | 在《现状》§3.4-3 里写明"年份自愈依附于秒刷"，改刷新策略时一并迁移 |
| 6 | LT-32 的"稳定"断言趋近恒真 | Blazor 的 diff 在"末尾追加一项"时不会重置 `value`（实测），所以坏实现未必被抓住 | 保留它作为低成本护栏，但**不能**把它当作"P-014 已修"的证据 |
