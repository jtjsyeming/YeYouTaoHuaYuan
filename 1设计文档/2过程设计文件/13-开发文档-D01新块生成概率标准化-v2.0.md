## 1. 现状基线

### 1.1 代码事实（`jtjsym/jtjsym/Pages/MyPage/Game_2048.razor`，337 行）

```csharp
// L44-46
private const int GridSize = 4;
private int[,] board = new int[GridSize, GridSize];
private Random random = new Random();          // ← 实例字段，非 Random.Shared

// L153-157  AddRandomTile() 的尾部
if (emptyTiles.Count > 0)
{
    var (row, col) = emptyTiles[random.Next(emptyTiles.Count)];
    board[row, col] = random.Next(1, 3) * 2;  // Adds 2 or 4   ← 唯一待改行
}
```

- **位置抽样**（`emptyTiles[random.Next(count)]`）是**均匀**的，符合标准 2048，不动；
- **值抽样**（`Next(1, 3) * 2`）在 `[1,3)` 上均匀 → 1/2 各 50% → 值是 2/4 各 50%。v1.0 判断正确。

### 1.2 调用链（修正 v1.0 的表述）

```
RestartGame()  L128 ──┬── AddRandomTile()  ×2      ← 开局两块
   ├ OnInitialized() L125（ServerPrerendered 下会走两遍：预渲染 + 电路）
   └ "重玩" / 遮罩内"重玩" 两个 @onclick

MoveLeft/Right/Up/Down L160-210
   └ AfterMove(before) L64 ── 若 IsBoardChanged == false → return（**不生成**）
                           └── AddRandomTile()  ×1  ← 每步有效移动
```

结论与 v1.0 一致（三处调用、改一个方法全局生效），但 `×1` 那一处是从 **`AfterMove()`** 发出的，键盘路径同样经 `AfterMove` —— 所以本次改动**天然覆盖键盘操作**，不需要额外验证分支。

### 1.3 实测（本次对运行实例执行，脚本与数据可复现）

| 项 | 实测值 | 方法 |
|---|---|---|
| 当前 4 的出现率 | **49/100 = 49.0%** | 连续点"重玩" 50 局，读 `.game-container .tile` 文本，只统计非零块 |
| 单局"点击→重渲染→读盘"往返 | **247 ~ 254 ms** | 同上，取 5 局均值与 50 局均值 |
| 50 局总耗时 | **12.7 s** | 含 50 次点击与 50 次读盘 |
| 单局两块是否独立 | 20 局中 7 局同时出现 2 与 4 | 理论 P=50%，7/20 在噪声内 |
| 每局块数 | 恒为 2，无异常值 | 100 个样本全部 ∈ {2,4} |

> 这组数据是本方案"可自动化"的实证基础：**13 秒换一条能挡住回退的确定性断言**，比"1 行代码直观保证"可靠得多。

### 1.4 标准规则

2048（Gabriele Cirulli 原版）：新块 **90% 为 2、10% 为 4**，位置在空格中均匀随机；开局的 2 块同规则。当前实现在"值"这一维上偏离标准，位置维正确。

## 2. 根因与影响

- **根因**：`random.Next(1, 3) * 2` 把"两种取值"顺手写成了"均匀分布"，不是有意设计。
- **定量**：新块期望值 `50/50 → 3.0`，`90/10 → 2.2`，**每步注入的数值压力下降 26.7%**；4 的出现频率由 `50%` 降到 `10%`（当前是标准的 **5 倍**）。
- **难度**：这是本页"比原版好打"的主要来源。修正后向标准靠拢；仍缺最高分持久化、撤销等，综合难度略低于原版，属正常。
- **不改变的**：每步仍只注入 1 块、注入位置仍均匀、`IsBoardChanged` 判据与调用时序不变。

## 3. 方案

### 3.1 选型（沿用 v1.0 的 A，补一个等价变体）

| 方案 | 思路 | 结论 |
|---|---|---|
| **A. 百分制整数抽样** | `random.Next(100) < 100 - FourSpawnPercent ? 2 : 4` | **采用**。一行、无浮点、百分比语义直接在代码里 |
| B. 浮点 `NextDouble() < 0.9` | 同效 | 否，引入浮点与精度讨论，无收益 |
| C. 权重表 / 可配置化 | 便于调参 | 否，单人小站无配置需求（YAGNI） |
| D. `random.Next(10) == 0 ? 4 : 2` | 更短，1/10 恰好 10% | 同效，但把"10%"藏进字面量，后续想调成 5% 要改两处 —— 不如 A |

### 3.2 最终代码（2 行）

```csharp
// ① @code 顶部，L44 的 GridSize 之后
private const int FourSpawnPercent = 10;   // 标准 2048：90% 出 2、10% 出 4

// ② AddRandomTile() 内，替换 L156
board[row, col] = random.Next(100) < 100 - FourSpawnPercent ? 2 : 4;
```

- `Next(100)` 返回 `[0,100)`，`< 90` 覆盖 90 个值 → 2 的概率恰 90%，其余 10 个值 → 4，**精确 90/10，无浮点误差**；
- 常量名带 `Percent`，落在 0~100 内即正确；若哪天写成 >100，`100 - x` 为负 → 恒出 4。属可控的"配置错误"，不值得为它加校验（const 在编译期固定）。

### 3.3 关于 `Random.Shared`（明确否决）

v1.0 把它列为"可选顺手项"。**不建议做**，理由不是风格而是可测性：

- `Random.Shared` 无法注入种子 → 后续若按 §10 抽 `Game2048Core` 做 xUnit，"给定种子 → 断言新块序列"这条路就断了；
- 实例字段还留着一个**不改代码就能做确定性测试**的钩子（构造函数 / 内部 setter 注入 `new Random(seed)`）；
- 行为变更与重构混在一个提交里，回滚粒度变差。

Tetris 用 `Random.Shared` 是因为它只需"随机方块"，从不打算复现序列 —— 两个页面的取舍本就不同，不必强行统一。

```js
// D-01：新块生成概率标准化（90% 出 2 / 10% 出 4）
// 手法：连续重开 N 局，只统计"初始两块"的取值——每局 2 个独立样本，不掺杂走棋逻辑。
import { test } from '@playwright/test';
import { check, open, readBoard, sleep } from './helpers.mjs';

const ROUNDS = 50;      // 50 局 → 100 个样本（实测 12.7s）
const MAX_FOUR = 25;    // 90/10 下期望 10（σ=3），25 已 +5σ

test.describe('D01 新块生成概率', () => {
  test('G2048-23 初始块取值分布：90% 出 2 / 10% 出 4', async ({ page }) => {
    test.slow();                                   // 实测 ~13s，60s 默认超时偏紧
    await open(page, '/game_2048', 1600);

    let c2 = 0, c4 = 0, bad = 0, samples = 0;
    for (let i = 0; i < ROUNDS; i++) {
      await page.locator('.replay-btn').first().click();
      await sleep(250);                            // 实测"点击→重渲染→读盘"往返 247ms
      const vals = (await readBoard(page)).flat().filter(v => v !== 0);
      if (vals.length !== 2) bad++;
      for (const v of vals) {
        samples++;
        if (v === 2) c2++;
        else if (v === 4) c4++;
        else bad++;
      }
    }

    const rate = samples ? ((c4 / samples) * 100).toFixed(1) : '0';
    check('G2048-23-取值域', bad === 0, `异常局/块 ${bad}（要求每局恰 2 块且值 ∈ {2,4}）`);
    check('G2048-23-上界', c4 <= MAX_FOUR, `4 出现 ${c4}/${samples}（${rate}%）；90/10 期望 10，上界 ${MAX_FOUR}`);
    check('G2048-23-下界', c4 >= 1, `4 出现 ${c4} 次（n=${samples} 下 0 次的概率 ≈2.7e-5）`);
  });
});
```

`tools/e2e/package.json` 增加一条：

```json

```

### 5.3 阈值为什么这么松却不漏（`n = 100, p = 0.1`）

| 指标 | 90/10（期望行为） | 50/50（回退到旧代码） |
|---|---|---|
| 4 的期望次数 | μ = 10 | μ = **50** |
| 标准差 | σ = √(100×0.1×0.9) = 3.0 | 5.0 |
| 上界 25 的位置 | **+5σ**，P(X ≥ 26) ≈ 1e-7 量级 | **−8.3σ**，必红 |
| 下界 1 的误报率 | P(X = 0) = 0.9¹⁰⁰ ≈ **2.7e-5**（约 1/37000 次运行） | 0（恒有大把 4） |

- 上界负责"抓回退"，余量 5σ，正常跑一万次也不会误报；
- 下界负责"抓另一个方向"（例如把常量写反成 90），误报率 2.7e-5；若想彻底消灭，把 `ROUNDS` 提到 100（26 s）→ 0.9²⁰⁰ ≈ 7e-10；
- **反向验证**：本文件 §1.3 的 49/100 就是用同一手法在**当前代码**上量出来的 —— 即该用例在改动前必红、改动后必绿，是先证伪再证真。
