## 1. 事实核对（全部实测或读码，非推测）

### 1.1 三处实现的口径对照

| 位置 | 表达式 | 口径 | 判定 |
|---|---|---|---|
| `LoveTime.razor:227` | `(now - t2).Days` | `TimeSpan.Days` = **向零截断**（正数即 floor） | **正确**（产品基准） |
| `Test/functiontest.mjs:125` | `Math.floor((now - t2) / 86400000)` | floor | **正确**（独立实现，与产品逐字一致） |
| `tools/e2e/tests/d03_calendar.spec.mjs:28` | `Math.round((now - t2) / 86400000)` | 四舍五入 | **错**（唯一离群者） |

前提已确认：`LoveTime.razor:208` 注释写明「anchor 恒为零点、n 含时分秒」，故 `(now - t2)` 的整数部分就是日历天差、小数部分就是当天的时刻比例——**round 在 ≥12:00 时必然进位 +1**。这就是"上午绿、下午红"的全部成因。

### 1.2 实测（2026-11-06 20:15，本机 CST）

```
$ npm run test:d03            # 未改动，Math.round
  3 failed  → LT-26 / LT-27 / LT-28
  LT-28：[LT-28] 期望 "8 年 6 个月 16 天"，实际 "8 年 6 个月 15 天"
  3 passed (57.7s)

$ # 仅把 L28 的 Math.round 改成 Math.floor，其余一字未动
$ npm run test:d03
  6 passed (45.2s)
```

偏差方向与报告一致：**测试期望比页面多 1 天**（页面 15、期望 16），说明错的是期望值那一侧，不是页面。试验后已 `git checkout -- tools/e2e/tests/d03_calendar.spec.mjs` 还原，工作区该文件干净。

### 1.3 LT-26 的三种锚点在 floor 下逐条成立（为什么不是"碰巧绿"）

| 锚点 | `t2` | `(now - t2)/86400000`（19:00 时） | floor | round（错） | 期望文案 |
|---|---|---|---|---|---|
| 今天 | 今天 00:00 | 0.79 | 0 | 1 | `不到 1 天` |
| 昨天 | 昨天 00:00 | 1.79 | 1 | 2 | `1 天` |
| 7 天前 | 7 天前 00:00 | 7.79 | 7 | 8 | `7 天` |

三者都只在 floor 下与页面一致；round 在 19:00 全偏 +1。**这不是"某个时刻的巧合"，而是 round 的系统性偏差**。

## 2. 修复方案

### 2.1 红线：改测试，不改产品

`TimeSpan.Days` 是**向零截断**。若把产品改成 `Math.Round((now - t2).TotalDays)` 去"迁就"测试，会制造一个真实缺陷：**用户在中午 12 点后看到天数凭空 +1**（一天之内跳两次）。而且 `Test/functiontest.mjs` 的独立实现已是 floor——改产品会让这条独立验证同时失效，两份证据一起被毁。

> 一句话：**页面 15 天是对的，期望 16 天是错的。** 判据 = 产品实现（`TimeSpan.Days`）与独立实现（`functiontest.mjs:125`）两方一致，d03 是唯一离群者。

### 2.2 最小改动（**1 个词**）

```js
// d03_calendar.spec.mjs:28
-  return { y, m, d: Math.round((now - t2) / 86400000) };
+  return { y, m, d: Math.floor((now - t2) / 86400000) };
```

**不做** v1.0 提议的"抽 `daysBetweenFloor` 公共函数"：全文件只有 1 处调用，抽函数只增加一层间接。改成 inline + 注释即可，`Math.floor` 与 C# 的 `(now - t2).Days` 在字面上就是同构的，可读性更好。

**注释放在 `ymd()` 定义上方**（v1.0 说"函数旁"，语义对，位置钉死）：

```js
/**
 * 期望值必须与产品同口径：LoveTime.razor:227 的 (now - t2).Days 是 TimeSpan 的**向零截断**（正数即 floor），
 * 而 Test/functiontest.mjs:125 的独立实现也是 floor。
 * 禁止改回 Math.round —— now 含时分秒，本地 12:00 之后 round 必然进位，会让 LT-26/27/28 上午绿、下午红（P-001）。
 * 冻结时刻自检见 LT-28 末尾的「口径」check。
 */
```

### 2.3 禁止触碰的 `Math.round`（I-03）

全仓其他 `Math.round` **一律不动**，它们都是几何/比例取整，与时间无关：

```
d02_keyboard_ui.spec.mjs:148,149,253   d11_d12.spec.mjs:83,97,138,150
d14_mobile_layout.spec.mjs:29,51       d15_home_fluent.spec.mjs:43,44,70,72,86
helpers.mjs:170,171,212,390,406
```

只按 `86400000` 这个特征串搜，不要去全局替换 `Math.round`。

## 5. 测试计划（把 v1.0 的"下午跑一次"换成可重复验收）

### 5.1 新增：冻结时刻口径自检（放进 LT-28）

`ymd(anchor, now)` 本就是**纯函数**（`now` 是入参，不读时钟），所以可以注入固定时刻——与真实时钟无关、任何时刻执行结果恒定：

```js
    // 口径自检（P-001 回归护栏）：同一锚点、同一天的两个时刻，天数必须相等。
    // 若有人把 floor 改回 round，19:00 会得 +1 天 → 这条立刻红，不需要等到下午才发现。
    const anchor = new Date(2018, 3, 22);
    const morning = ymd(anchor, new Date(2026, 10, 6, 9, 0, 0)).d;
    const evening = ymd(anchor, new Date(2026, 10, 6, 19, 0, 0)).d;
    check('LT-28-口径', morning === evening, `同一天 09:00 与 19:00 的天数必须相等：${morning} vs ${evening}（相等=截断口径，差 1=有人改回了 round）`);
```

这条是本修复**唯一能防复发**的東西：成本 4 行、耗时 0.1ms、不依赖真实时钟、不新增用例编号。

### 5.2 门禁

1. `npm run test:d03` → **6 passed**（实测修复后 45.2s）；
2. `npm run test:lt` → 10 通过（副行与主计时共用同一渲染路径）；
3. `npm run test:d11d12` → 7/7（D-12 的裁切断言就在 `.timer-display` 上，与 `calendarElapsed` 同页同源）；
4. `npm run test:smoke` → 6 通过 1 跳过（LT-01 的 `div.timer===3` 依赖副行只带 `.timer-calendar`，本次不动 markup）；
5. `dotnet build -c Release --no-incremental` → 0 警告 0 错误（本次不改 C#，此步是排除"误改产品"的最后一道闸）。

### 5.3 时刻鲁棒性（替代 v1.0 的"下午跑一次"）

- **必做**：§5.1 的冻结时刻自检已在门禁里，每跑一次都在验口径；
- **建议**：在下午/晚间再跑一次 `node Test/functiontest.mjs --only FT-13,FT-17`，人工确认输出里 `floorMismatchCount === 0`、`roundMismatchCount === 3`（下午）。这一步是**交叉验证**（用完全独立的实现再看一遍），不是门禁项；
- 若只在上午执行过 §5.2，**不能**据此宣称"已验证时刻鲁棒性"——那正是 P-001 当初漏网的原因。
