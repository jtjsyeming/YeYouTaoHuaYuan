## 1. 问题与现状

### 1.1 H-001 / D-04：暂停期间难度仍升级

`Tetris.razor`（实测行号，实施时以当前代码为准）：

```csharp
private void PauseGame()      // :1008
{
    if (isDisposed) return;
    isPaused = true;
    gameTimer?.Stop();        // 只停主下落
    StopSoftDrop();           // 内部 :750 有 !isPaused 守卫，不会误启 gameTimer
    StateHasChanged();
}

private void ResumeGame()     // :1018
{
    if (isDisposed) return;
    isPaused = false;
    gameTimer?.Start();       // 只启主下落，不校正 Interval
    StateHasChanged();
}
```

`difficultyTimer`（180000ms，`AutoReset=true`，`:684`）全程未受暂停影响。两层后果（与 11-06 报告 TRIS-26 实测一致）：

1. 暂停 3 分钟后 `IncreaseDifficulty()` 照常触发，等级 +1；
2. `IncreaseDifficulty()` 第 `:1003` 行写 `gameTimer.Interval = speed`——`gameTimer` 虽已停，但 `ResumeGame()` 只 `Start()` 不恢复 Interval，**恢复后下落直接变快**。

用户感知为「暂停一下反而更难了」，且全程静默。

**v1.0 三条「核对项」的查证结果（v2.0 新增）**：

| 核对项 | 现状（实测行号） | 结论 |
|---|---|---|
| `OnDifficultyTimerElapsed` 有无 `isPaused` 守卫 | `:797` 回调，`:803` 只判 `!isGameOver` | **缺口，必须补**。Stop 与"回调已入队→`InvokeAsync` 执行"之间存在窗口，此时 `isPaused` 已为 true 但回调仍会跑到 `IncreaseDifficulty()` |
| `IncreaseDifficulty()` 是否自带守卫 | `:994-996` 只有 `if (isDisposed) return;` | 建议把守卫加在**这里**（单一收口），而不是只加在回调里——一行覆盖所有入口 |
| `GameOver()` 是否停了 `difficultyTimer` | `:1037-1044`：`isGameOver=true; StopTimers();`，`StopTimers()`（`:691`）对两个 Timer 都 `Stop + -= + Dispose + null` | **已正确，无需改动**（v1.0 担心的"结束挂 3 分钟也升级"不成立） |
| `RestartGame()` 是否残留被改小的 Interval | `:1027-1035`：`StopTimers(); InitializeGame(); … StartGame();`；`InitializeGame()` 把 `speed` 复位为 `INITIAL_SPEED`，`StartTimers()` 用 `speed` 新建 Timer | **已正确，无需改动**（暂停→重开路径的 Interval 天然干净） |
| `StopSoftDrop()` 会不会在暂停时误启 `gameTimer` | `:750` `if (!isPaused && !isGameOver && gameTimer != null && !isDisposed)` | 正确：`PauseGame` 先置 `isPaused` 再调 `StopSoftDrop` |
| `Dispose()` / `DisposeAsync()` | 均走 `StopTimers()` | 正确 |

## 2. 根因（4 个独立成分）

### 2.1 cell-size 只有宽度维度

`:193` 的公式只按 `100vw` 收缩，格子取满 30px 上限后画布 604px 固定，任何矮视口都会截断底部两行——用户最痛的点（方块落到底部看不见）就是这一条。

### 2.2 侧栏面板才是高度约束

844×390 实测：`.side-panel` 高 **300.5px**（padding 24 + 3 组信息行 + 预览 62 + 暂停/重开两颗 36px 按钮 82）。`top-area` 是 `align-items: flex-start` 的行容器，高度取 `max(画布, 面板)`。所以：

- cell 缩到 12px → 画布 252px < 面板 300.5px → **top-area 仍按 300.5 算**，页面总高不变；
- 实测 B 组（预算 142）与 A 组（预算 100）溢出量**同为 48px**，格子多缩了 2px 却零收益。

**结论：不压缩面板，cell 缩到 1px 也消不掉那 48px。**

### 2.3 641~780px 短视口仍纵向堆叠

L2（`:477`）为「窄窗真空区」设计，把面板堆到画布下方（实测 700×900 正确）。但横屏手机 667/740 宽正好落在这一区，堆叠后面板底到 970px，比 360px 视口高 610px——**暂停/重开按钮根本滚不到**。短视口需要的是横排而非堆叠。

### 2.4 min-height 少算 17.6px

`:188` `min-height: calc(100vh - 30px)` 只扣了标题 30px，没扣 `.content` 的 `padding-top: 1.1rem`。实测改前 1400×1000 溢出 18px、改后 0px（G 组），**逐像素对齐**。

## 3. 修复方案

### 3.1 D-04：暂停时同时冻结 difficultyTimer

```csharp
private void PauseGame()
{
    if (isDisposed) return;
    isPaused = true;
    gameTimer?.Stop();
    difficultyTimer?.Stop();     // 新增
    StopSoftDrop();
    StateHasChanged();
}

private void ResumeGame()
{
    if (isDisposed) return;
    isPaused = false;
    gameTimer?.Start();
    if (gameTimer != null) gameTimer.Interval = speed;   // 可选兜底：让 Resume 对 Interval 幂等
    difficultyTimer?.Start();    // 新增
    StateHasChanged();
}

private void IncreaseDifficulty()
{
    if (isDisposed || isPaused || isGameOver) return;     // 单一收口，替代"回调里再加一次判断"
    …
}
```

**语义决策（必须在实施时定稿并写进注释）**：`System.Timers.Timer.Stop()` 会作废本轮倒计时，`Start()` 从满周期重算。即「暂停 179 秒后继续」会重新获得完整 180 秒。这符合「暂停冻结一切」的直觉，但等价于**主动暂停可无限延后升级**。方案里接受这一点（升级只是变难，延后无收益激励）；若日后要求「按累计游戏时长升级」，需换成 `Stopwatch` 累计而非依赖 `Interval`，属另一条目，本单不做。

线程口径：`Stop()`/`Start()` 本身线程安全，`PauseGame` 不额外加 `timerLock`（与现有 `gameTimer?.Stop()` 风格一致）；真正的竞态窗口由 `IncreaseDifficulty()` 首行守卫关闭。

### 3.2 H-006：4 项联动（推荐方案 R1）

| 项 | 内容 | 作用 |
|---|---|---|
| ① | `--cell-size` 加第三项 `calc((100dvh - 142px) / 20)` | 按高度收缩格子，让 20 行进得去 |
| ② | `@media (max-height: 430px)` 压缩面板与操作区 + 容器 `padding: 10px → 6px` | 把 300.5 压到 238.5，让面板不再当约束 |
| ③ | `@media (min-width:641px) and (max-width:780px) and (max-height:430px)` 解除 L2 堆叠 | 让 667/740 横屏回到「画布左、面板右」 |
| ④ | `min-height` 由 `calc(100vh - 30px)` 改 `calc(100dvh - 30px - 1.1rem)` | 补上 17.6px，让「零滚动」真的为 0 |

**① 的 142px 预算推导**（844×390 实测逐项）：`.content` 上内边距 17.6 + `h1` 24 + 下边距 6 + 容器 `padding-top` 10 + 画布上边框 2 + 下边框 2 + `gap` 15 + 操作区 55 + 容器 `padding-bottom` 10 = **141.6 ≈ 142**。写成 `calc((100dvh - 142px) / 20)`（20 = `GRID_HEIGHT`）。

**用 `100dvh` 不用 `100vh`**：真实手机横屏时浏览器工具栏会伸缩，`100vh` 取"大视口"会高估可用高，导致格子偏大仍溢出；而 Playwright 的 `viewport` 恒等于 `innerHeight`，**测试永远看不出这个差别**。站内 ≤520px 段（`:513`）已用 `100dvh`，口径统一。

**实测对照（横屏四档，`addStyleTag` 注入）**：

| 组 | 改动 | cell | 画布底 | 面板底 | 控件底 | 纵向溢出 |
|---|---|---|---|---|---|---|
| A | v1.0 方案（预算 100） | 844:14.5 / 812:13.75 | 351.6 | 358.1 | 未达 | **48 / 63** |
| B | 预算 142 单独 | 844:12.39 / 812:11.64 | 309.4 | 358.1 | 未达 | **48 / 63**（同 A，纯损失） |
| C | 142 + ②（含字号压缩） | 844:12.39 | 305.4 | 226.5 | 未达 | **18**（= ④ 的残留） |
| D | C + ③ | 844:12.39 / 812:11.64 / 740:10.89 / 667:11.64 | 305.4 / 290.4 / 275.4 / 290.4 | 238.5 | 375.4 / 362.1 / 362.1 / 362.1 | **18 / 18 / 18 / 18** |
| **E** | **D + ④（推荐）** | 同上 | 同上 | 同上 | 同上 | **0 / 0 / 8 / 0** |
| F | 只加"网格可见"预算 62（备选 R2） | 844:16.39 / 812:15.64 | 389.4 / 374.4 | 358.1 | **459.4 / 444.4** | 79 / 79 / 388 / 388 |

两条从实测读出来的判断：

- **B 组证明"越缩越好"是错觉**：844 档 A 与 B 的溢出完全相同（48px），B 只是把格子从 14.5 白缩到 12.39。所以 ① 的预算**必须和 ②/③/④ 配套才有意义**，单独上 ① 等于只做视觉降级；
- **740×360 剩 8px**（面板 238.5 才是这档的约束，继续调 ① 的预算无效）。二选一：把该档断言放宽到 `innerH + 10px`，或在 ② 里再压 8px（`.next-piece-preview` `min-height` 40→32、`.control-btn` 30→28）。推荐后者，实施时复验。

### 3.3 备选方案 R2（最小改动，只解用户痛点）

只做 ①，预算取 62px（`calc((100dvh - 62px) / 20)`）：画布底 ≤ 视口高在四档全部成立（389.4 / 374.4 / 359.4 / 374.4），格子能保住 14.9~16.4px。代价：

- 页面仍溢出 79px（844/812），操作区要滚动一下才看得到；
- 740/667 档面板仍在画布下方（面板底 667.9 / 682.9），**暂停/重开按钮要滚很久**。

**推荐 R1**：H-006 的原始诉求是"横屏也得能正常玩"，R2 只让棋盘可见、控制区仍要滚动，等于把问题挪到下一版。R1 的代价是 844×390 下格子降到 12.4px、画布 124×248 居中在 538px 宽的区域里（**横向大片留白**）——观感确实不如 30px。若评审否决 12px，请退 R2 并明确写"控制区允许滚动"，不要留成"既没零滚动又白缩格子"的 B 组状态。

> 可选的后续优化（**本单不做、未实测**）：短横屏把 `.bottom-area` 改为同排第三栏（画布 | 面板 | 操作），按几何估算格子可回到 ~15px 且零滚动。属布局重构，另立条目。

**断言口径（关键）**：

```js
// 硬断言：棋盘与面板完整可见（这是用户痛点）
check('D14-10', m.canvas.bottom <= m.vh && m.panel.bottom <= m.vh, …);
// 软断言：操作区完整可见；740×360 允许 10px 内溢出（面板是硬约束，见 §3.2）
check('D14-10b', m.controls.bottom <= m.vh + 10, …);
// 横向不回归
check('D14-10c', m.scrollW <= m.clientW, …);
```

**不要用 `scrollHeight <= innerHeight` 当横屏判据**——除非 ④ 同批落地。当前代码在 1400×1000 就恒溢 18px（实测），这个判据在实施前是必红、实施后才是真信号，容易把"没修 min-height"误判成"cell 公式错"。

### 5.3 回归

1. **桌面零变化**：1400×1000、1280×800、1024×768 用 `getComputedStyle` 断言 `--cell-size` 计算值仍为 30px，且 `scrollHeight`（④ 落地后）≤ `innerHeight`；
2. **竖屏零回归**：`D14-1/D14-2/D14-7` 七档（含 320×568→15.0、375×667→20.5、520×900→30）必须保持全绿——④ 改的是 base 段 `min-height`，≤520px 段有自己的 `calc(100dvh - 74px - 30px)`，②③ 的 `max-height:430px` 也进不去这七档；
3. **L2 堆叠不回归**：`D14-9-堆叠`（700×900）必须仍然 `panel.top > canvas.bottom`——③ 带 `max-height:430px` 条件，900 高不命中；
4. **暂停/结束态布局**：`D14-6`（375×667，暂停面板变高、结束态多一行提示）必须仍全绿——② 只改矮视口，不影响它；
5. **门禁**：`npm run test:tris`（TRIS-14 320s + TRIS-26 240s，单文件约 10 分钟）→ `test:d14` → `test:smoke` → 登记 `9测试用例固定执行历史` → 关闭 H-001/H-006 → 更新两份台账。

### 5.4 手工确认（自动化覆盖不到的）

1. 真机横屏（Chrome Android / Safari iOS）转屏一次，确认 `100dvh` 在工具栏伸缩时不抖动、暂停/重开可点；
2. 暂停 3 分钟 → 继续，确认等级与下落速度都不变（TRIS-26 的自动化版会跑，但真机一次更直观）；
3. 暂停 1 分钟 → 继续 → 再等 2 分钟，确认**不会**因为"重新计时"而立刻升级（验证 §3.1 的语义决策被正确实现）。
