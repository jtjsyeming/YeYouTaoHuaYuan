## 1. 检视结论

v1.0 的**问题诊断（首屏只见网格、按钮在 3 屏之外）、方案选型（`display: contents` + Grid 重排）、"零 DOM / 零 JS / 纯 CSS"的约束**都成立，我实测复现了它的核心判断：375×667 下现状 `scrollHeight = 1061`（约 1.6 屏），信息面板在 y=689、操作按钮在 y=1005，确实是"要滑两下才够得着"。

但按 v1.0 的代码块**原样实施会得到 3 个可复现的偏差**，另有 5 处事实/口径需要修正：

| # | 严重度 | v1.0 的问题 | 实测证据 |
|---|---|---|---|
| 1 | **高（必修）** | `.side-panel` 的 `width: auto; min-width: 0` 只写在正文 L118，**代码块里没有** | 若只照代码块实现（L2 的 `width: calc(var(--cell-size)*10+4px)` + `max-width:100%` 仍在）→ 320px 下 **面板宽 114 而按钮区宽 124**，右栏两块右边缘差 10px，肉眼可见错位 |
| 2 | **高（必修）** | 缺 `align-self: start` | 画布在跨两行的区域里**垂直位置不稳定**：375px 下 canvas y=**113.3**（比面板低 29.7px），414px 下 y=**83.6**（与面板齐平）。原因：画布高 334 < 右栏 393.5 时被居中，> 时贴顶 |
| 3 | **高（验收口径）** | "667px 高的屏幕**一屏放下，无需滚动**"按原方案不成立 | `.tetris-container` 有 `min-height: 100vh`，上方还有导航 56 + `.content` `padding-top: 1.1rem(17.6)` → 文档高**恒为 741**（320/360/375/414/520 六档实测 `scrollHeight` 全是 741 > `clientHeight`）。内容确实都在首屏（按钮底边 477 < 667），但页面永远能往下滚 74px 黑边。→ 目标改述为**"全部控件首屏可见、无需滚动即可操作"**；若要求真的没有滚动条，见 §2.3 的 `min-height` 换算式（实测 `scrollHeight == clientHeight`） |

| 6 | 中（算式错、结论对） | ←↓→ 宽"约 37px"，但推导写成 `(124−16−12)/3 = 32` | 实测 375px 下三键 **37.3 × 52**（`.direction-pad` 无 padding，正确算式 `(124−12)/3 = 37.3`）。且 ≤360 收窄后曾是 **37.3 / 33.5 / 37.3 不等宽**（受 `min-width:auto` 的 min-content 下限），需 `min-width: 0` 才等分 |
| 7 | 中（估反了） | "右栏 ≈314 < 网格 334，左右底边基本对齐" | 实测面板 **274.5** + 行间距 + 操作区 **104** = **386.5**，**高于** 375 的网格 334。320/360 档更是面板 274.5 vs 网格 304/384 → **右栏先到底**，网格下方留白。不是致命问题，但描述与事实相反，会影响后续判断 |
| 8 | 低 | 用例只压 375×667 | 补 320×568（iPhone SE）、360×640、460（30px 封顶前一档）、521/640（横排边界回归） |

## 2. 修订后方案

**核心不变**：≤520px 用 `display: contents` 抹掉 `.top-area`/`.bottom-area` 两个包装层，让 `.game-area`/`.side-panel`/`.control-buttons` 直接成为 `.tetris-container` 的 grid 项，排成"左棋盘 / 右信息 + 操作"。**razor 标记零改动、零 JS、纯 CSS。**

相对 v1.0 的实质改动是 **4 处补丁 + 1 处预算重算**：

1. 把 `.side-panel` 的宽度覆盖**写进代码块**（问题 1）；
2. `align-self: start` 固定画布/面板的垂直对齐（问题 2）；
3. `min-height: calc(100dvh − 74px)` 消除文档级的 74px 溢出（问题 3，可选项，推荐一并做）；
4. 右栏由 124 → **132**，并**取消 v1.0 的 `≤360px` 收窄档**（问题 6，132 在 320px 下也放得下，少一个断点、按钮保持 40px）；
5. 走**满宽**（`margin: 0 -24px`）重算格子预算：`--cell-size: min(30px, calc((100vw - 170px)/10))`（问题 5）。

### 2.1 尺寸预算（重算并实测）

```
满宽后可用宽 = 100vw − 容器 padding 20            （article 的 px-4 被 -24px 抵消）
棋盘可用宽   = 上述 − 列间距 8 − 右栏 132 − 画布边框 4 − 余量 6
             = 100vw − 170
--side-col : 132px
--cell-size: min(30px, calc((100vw - 170px) / 10))
```

| 视口 | 格子 | 画布（宽×高） | 右栏 | 画布底边 | 最后一颗按钮底边 | 横向溢出 | 纵向滚动 |
|---|---|---|---|---|---|---|---|
| 320×568 | 15.0px | 154×304 | 132 | 388 | **470** | 无 | 无（568） |
| 360×640 | 19.0px | 194×384 | 132 | 468 | **470** | 无 | 无（640） |
| 375×667 | **20.5px** | 209×414 | 132 | 498 | **491** | 无 | 无（667） |
| 390×844 | 22.0px | 224×444 | 132 | 528 | 513 | 无 | 无（844） |
| 414×896 | 24.4px | 248×492 | 132 | 575 | 549 | 无 | 无（896） |
| 460×800 | 29.0px | 294×584 | 132 | 668 | 619 | 无 | 无（800） |
| 520×900 | 30.0px（封顶） | 304×604 | 132 | 688 | 633 | 无 | 无（900） |

对照 v1.0 的 375px：格子 16.5 → **20.5**，画布 169×334 → **209×414**；按钮 37.3×52 → **40×52**；旋转 124×44 → **132×44**；暂停/重开 112×38 不变。

> 375×667 的纵向账：导航 56 + `.content` 上边距 17.6 + 容器 padding 10 + **画布 414** = **497.6**，右栏底边 490.7 —— 全部在 667 之内，余量 176px。320×568 最紧的一档也有 98px 余量。

### 2.2 完整替换 CSS（可直接粘贴进 `Tetris.razor` 的 `<style>`，替换 L430-L486 三段媒体查询）

```css
/* L1：≤900px 放开 80%（不变） */
@media (max-width: 900px) {
    .top-area { width: 100%; }
}

/* L2（改造后）：只剩 641~780px 的"窄窗真空区"堆叠。
   ≤520px 段整体撤销，交给 L3 的 Grid 重排接管 —— 这是 v1.0 "改动 1" 的正确落法 */
@media (min-width: 641px) and (max-width: 780px) {
    .top-area {
        width: 100%;
        flex-direction: column;
        align-items: center;
        gap: 8px;
    }

    .game-area {
        flex: none;
        width: auto;
    }

    .side-panel {
        flex: none;
        box-sizing: border-box;                    /* 否则外宽比网格多 28px */
        width: calc(var(--cell-size) * 10 + 4px);  /* +4px 对齐画布边框 */
        max-width: 100%;
        min-width: 0;
    }
}

/* L3（新增）：≤520px 手机——左棋盘 / 右「信息 + 操作」。
   桌面 ≥521px 各档实测与本改动前逐项一致（canvas/panel/controls 的 x/y/w/h 全等） */
@media (max-width: 520px) {
    .tetris-container {
        display: grid;
        grid-template-columns: auto var(--side-col);
        grid-template-areas:
            "canvas panel"
            "canvas controls";
        align-content: start;
        justify-content: center;
        column-gap: 8px;
        row-gap: 8px;                 /* 覆盖容器原有的 gap:15px，右栏更紧凑 */
        margin: 0 -24px;              /* 满宽：抵消 article 的 px-4，把 48px 让给棋盘 */
        min-height: calc(100dvh - 74px);  /* 74 = 导航 56 + .content padding-top 17.6 */
        --side-col: 132px;
        /* 170 = 容器 padding 20 + 画布边框 4 + 右栏 132 + 列间距 8 + 余量 6 */
        --cell-size: min(30px, calc((100vw - 170px) / 10));
    }

    /* 抹掉两个包装层，孙级直接成为 grid 项（razor 标记零改动） */
    .top-area,
    .bottom-area { display: contents; }

    .game-area       { grid-area: canvas;   align-self: start; }
    /* width/min-width 必须写：L2 的 calc(...) 与 max-width 会串到这里，导致面板比按钮区窄 10px */
    .side-panel      { grid-area: panel;    align-self: start;
                       width: auto; min-width: 0; box-sizing: border-box; padding: 8px; }
    .control-buttons { grid-area: controls; }

    /* 信息面板紧凑化 */
    .next-piece-preview { min-height: 44px; padding: 6px; }
    .divider            { margin: 2px 0; }
    .control-btn        { height: 38px; font-size: 13px; }

    /* 操作区：旋转独占一行，←↓→ 一行三列（弹性等分） */
    .control-buttons { flex-direction: column; width: 100%; gap: 8px; }
    .direction-pad   { flex-direction: column; gap: 8px; width: 100%; }
    .rotate-btn      { width: 100%; height: 44px; font-size: 16px; }
    .dir-buttons     { width: 100%; gap: 6px; }
    /* min-width:0 必写：否则 ←/→ 的 min-content(37.3) 会挤掉 ↓，三键变成 37.3/33.5/37.3 */
    .direction-btn   { flex: 1; min-width: 0; width: auto; height: 52px; font-size: 20px; }
}

/* L4：v1.0 的 ≤400px 定宽缩档整段删除 —— 新方案用 flex 等分，定宽会与之打架；
   132px 右栏在 320px 下实测仍有 6px 余量，不再需要 ≤360px 的收窄档 */
```

**要点**

- `--side-col` 在声明之前就被 `grid-template-columns` 引用没问题：自定义属性在计算值阶段解析，同一条规则内声明顺序无关（已实测）；
- `display: contents` 让 `.top-area`/`.bottom-area` 不产生盒子，其自身的 `width:80%`/`flex-direction:column`/`gap` 全部失效，**不需要额外清理**；
- `.game-area` 的 `flex: 3`、`.bottom-area` 的 `max-width: 600px` 在 grid 项身份下同样无害；
- `margin: 0 -24px` 硬编码了 Bootstrap `px-4` 的 24px —— 若将来改版心宽度，这里要同步（可改 `margin: 0 calc(-1 * var(--page-pad))` 但要先在布局层定义该变量）；
- 底色：`.tetris-container` 本身是 `#0a0a0a`，满宽后黑底直达屏幕边缘，手机观感比"白边包一块黑板"更像游戏。

### 2.3 三种布局的取舍（供决策，默认取 A）

| 方案 | 375px 格子 | 375px 按钮 | 改动 | 评价 |
|---|---|---|---|---|
| **A. 满宽 + 右栏 132（本文默认）** | **20.5px** | 40×52 | `margin: 0 -24px` 一行 | 棋盘 +24%、按钮 +7%，代价只是取消本页左右留白 |
| B. 破版心 + 右栏 124（= v1.0 原案） | 16.5px | 37.3×52 | 无 | 保住了白边，但格子明显偏小 |
| C. 按钮 `position: fixed` 底部拇指区 | 30px（满格） | 55×55 | 较多 | 会遮挡内容、需处理 safe-area，且用户明确要"在右边"，不取 |

若担心满宽观感，A → B 只需删掉 `margin` 那行、把 `132→124`、`170→210`。

| 风险 | 影响 | 缓解 |
|---|---|---|
| `display: contents` 兼容性（iOS Safari 11.1+ / Chrome 65+） | 更老的 WebView 退化为纵向堆叠 | 堆叠是已验证的可用形态，属优雅降级；不做 polyfill |
| `min-height: calc(100dvh - 74px)` 里 74 是硬编码（导航 56 + `.content` 17.6） | 若以后改导航高度，会多/少一条细滚动条 | 注释写明来源；不追求完美时可直接删这行，退回"内容在首屏但可下滚 74px 黑边" |
| `100vw` 含经典滚动条 | 桌面窗口拖到 ≤520px 时横向溢出约 9px（无头浏览器测不出） | ①真机/真实 Chrome 手工确认一次；②加固：给 `.tetris-container` 加 `container-type: inline-size`，改用 `--cell-size: min(30px, calc((100cqw - 144px)/10))`（`cqw` 基于内容盒，见 §7） |
| 方向键 40px < 44px（Apple HIG） | 误触率略高 | 40 是"棋盘 20.5px 格子"下的最优折中；如需 44，则右栏要 148px、格子降到 18.6px，得不偿失 |
| 320px 格子 15px、6 类方块辨识吃力 | 可玩性 | 该档机型占比极低；如实记录，不做特殊处理 |
| 子像素（20.5px 等非整） | 网格出现发丝缝 | 08 已有 `.grid-cell{border + box-sizing}` 处理，实测无双线 |
| 平板横屏（如 1024×768）落在桌面档 | 无变化 | 本次目标就是零变化 |

**回退**：单个 `<style>` 块内还原（`git checkout -- jtjsym/jtjsym/Pages/MyPage/Tetris.razor`），无数据/接口副作用。

## 7. 可选加固：用容器查询单位替代 `100vw`（不在本次范围）

```css
.tetris-container { container-type: inline-size; }        /* 建立容器上下文 */
@media (max-width: 520px) {
    .tetris-container { --cell-size: min(30px, calc((100cqw - 144px) / 10)); }
}
/* 144 = 画布边框 4 + 右栏 132 + 列间距 8；100cqw 是容器内容盒宽，天然不含滚动条、也不含 article 的 padding */
```

优点：一次干掉"`100vw` 含滚动条"和"`-24px` 硬编码版心"两个隐患。代价：兼容底线从 2018 抬到 2023（Chrome 105 / Safari 16 / Firefox 110）。**建议先按 §2.2 落地，等 `cqw` 兼容线不再是问题时再切**（两者数值等价，切换只改 1 行）。
