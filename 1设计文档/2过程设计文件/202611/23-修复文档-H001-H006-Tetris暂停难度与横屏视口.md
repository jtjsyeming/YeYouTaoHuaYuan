## 1. 问题与现状

### 1.1 H-001 / D-04：暂停期间难度仍升级

`Tetris.razor`（实测行号，实施时以当前代码为准）：

```csharp
private void PauseGame()      // :1008
{
    if (isDisposed) return;
    isPaused = true;
    gameTimer?.Stop();
    StopSoftDrop();
    StateHasChanged();
}

private void ResumeGame()     // :1018
{
    if (isDisposed) return;
    isPaused = false;
    gameTimer?.Start();
    StateHasChanged();
}
```

`PauseGame()` 只停了 `gameTimer` 和软降，**没停 `difficultyTimer`**。后果有两层（报告实测 TRIS-26）：

1. 暂停 3 分钟后 `IncreaseDifficulty()` 照常触发，等级 +1；
2. `IncreaseDifficulty()` 还会改小 `gameTimer.Interval`——虽然 `gameTimer` 已停，但 Interval 被改了，`ResumeGame()` 只 `Start()` 不恢复 Interval，恢复后下落突然变快。

违反"暂停冻结一切"的直觉，且是静默发生的（用户感知为"暂停一下反而更难了"）。

### 1.2 H-006：横屏手机玩 Tetris 仍需纵向滚动

`--cell-size` 公式（`:193`）只按视口**宽度**收缩：

```css
--cell-size: min(30px, calc((100vw - 78px) / 10));
```

844×390 横屏下：宽度 844px 足够，格子取满 30px 上限，网格高 20 × 30 = **600px**，远超 390px 视口高，必须纵向滚动（看不到底部两行，方块落到底部时不可见）。

## 2. 修复方案

### 2.1 D-04：暂停时同时停 difficultyTimer

```csharp
private void PauseGame()
{
    if (isDisposed) return;
    isPaused = true;
    gameTimer?.Stop();
    difficultyTimer?.Stop();     // 新增：暂停冻结难度
    StopSoftDrop();
    StateHasChanged();
}

private void ResumeGame()
{
    if (isDisposed) return;
    isPaused = false;
    gameTimer?.Start();
    difficultyTimer?.Start();    // 新增：恢复后难度计时从零继续
    StateHasChanged();
}
```

实施时须核对三处一致性（改动清单内列明）：

- `RestartGame()` 里两个计时器的 Interval 重置逻辑是否完整（暂停→重开路径不得残留被改小的 Interval）；
- `difficultyTimer` 的 Elapsed 回调里是否已有 `isPaused` 守卫（理论上 Stop 后不会触发，但 Timer 停止与回调在跑之间存在竞态，双保险成本为零）；
- 游戏结束路径 `GameOver()` 是否也停了 `difficultyTimer`（若只停 gameTimer，结束画面挂 3 分钟同样会升级）。

### 2.2 H-006：--cell-size 加入 vh 维度

```css
--cell-size: min(30px, calc((100vw - 78px) / 10), calc((100vh - 100px) / 20));
```

- **原理**：`min()` 取三者最小。桌面全屏窗口高度充足，第三项远大于 30px，恒不生效——**桌面视觉零变化**（与《08》方案的兼容方式相同）；
- **844×390 横屏**：第三项 = (390 − 100) / 20 = **14.5px**，网格高 290px，一屏放下；
- **100px 预算的构成**：h1 标题行 ≈30px + 页面纵向 padding/边距 ≈40px + 缓冲 ≈30px。实施时在 844×390、740×360、667×375 三档实测校准，允许 90~110px 间微调；
- **副作用声明**：桌面用户把窗口压得很矮时网格也会收缩——这是正确行为而非回归（否则同样要滚动）；
- `:188` 的 `min-height: calc(100vh - 30px)` 容器约束与本改动不冲突，实施时确认即可。

## 4. 测试计划

1. **TRIS-26 解锁**：去 `fixme` 后按原判据跑（暂停 3 分钟→继续→断言等级不变、下落速度不变）。3.5 分钟的用例保留在**全量套件**（不进冒烟集），这是它当初被 fixme 的唯一原因；
2. **横屏矩阵**（Playwright viewport）：844×390、740×360、812×375——断言 `scrollHeight <= innerHeight`（无需纵向滚动）+ 网格底行在视口内；
3. **桌面回归**：1400×900、1024×768 下 `--cell-size` 计算值仍为 30px（getComputedStyle 断言），保证零视觉变化；
4. **竖屏回归**：375×667、320×568 断言与《11》验收一致（第三项在这些视口大于第二项，不改变结果）；
5. **门禁**：`npm run test:tris + test:d14 + test:smoke` 全绿 → 登记执行历史 → 关闭 D-04 → 更新两份台账文档。
