## 1. 背景与根因

用户诉求：玩 2048 途中切到别的页面、返回上一页、或手机切后台，回来后**本局进度丢失**，希望"本次访问"内回来能接着玩。

**根因（三条路径殊途同归）**——2048 的状态（`board`/`Score`/`isGameOver`）全部活在组件实例内存里，而 Blazor Server 下组件实例随时会死：

| 场景 | 发生了什么 |
|---|---|
| 站内切页 / 返回上一页 | NavLink 客户端路由 → 组件 `Dispose`；回来时 `OnInitialized` 重跑 → 全新开局 |
| 手机切后台 / 锁屏 | SignalR 断线，默认重连超时后 **circuit 销毁**；回浏览器时 `_Host` 重新预渲染 + 建 新 circuit → 全新组件实例 |
| 刷新页面 | 同上，circuit 重建 |

这不是 bug 而是托管模型的必然——解法只有一个：**把对局状态持久化到浏览器侧，回来时恢复**。

## 2. 存储选型："本次访问" = sessionStorage

| 方案 | 语义 | 结论 |
|---|---|---|
| **A. sessionStorage（推荐）** | 标签页会话级：切页/刷新/切后台都在，**关标签或关浏览器自动清除** | **采用**。与"本次访问"逐字匹配；新开标签自然开新局（符合直觉）；不会出现"三天后打开还是上次的残局" |
| B. localStorage（best 所用） | 跨会话永久 | 否。残局保存数天再恢复，体验怪异；best 是"纪录"该永久，进度是"过程"该会话级——**两者分工恰好构成完整语义** |
| C. 服务端（circuit 外缓存） | 内存字典 | 否。circuit 销毁即丢（正是要解决的问题）；引入全局状态与并发清理，得不偿失 |

键名：`jtjsym.g2048.session`（沿用 C-06 确立的 `jtjsym.` 命名空间约定）。

## 3. 详细设计

### 3.1 序列化格式（一个必踩的坑先钉死）

`board` 是 `int[,]`，**System.Text.Json 不支持多维数组**（直接序列化抛 `NotSupportedException`）——必须转扁平数组。存档 DTO：

```json
{ "v": 1, "cells": [2,0,4,0, 0,2,0,0, ...16 个...], "score": 1234 }
```

- `v` 版本号：未来棋盘结构变化时丢弃旧档而非错解；
- `cells` 行优先扁平：`board[i / 4, i % 4]`；
- **不存 `isGameOver`**：恢复后用 `IsGameOver()` 重算（单一事实源，杜绝"存档说没结束、棋盘实际已死"的不一致）。

### 3.2 写入：挂在既有汇聚点，即时落盘

```csharp
private async Task SaveSessionAsync()
{
    try
    {
        var cells = new int[GridSize * GridSize];
        for (int r = 0; r < GridSize; r++)
            for (int c = 0; c < GridSize; c++)
                cells[r * GridSize + c] = board[r, c];
        var json = JsonSerializer.Serialize(new SessionState(v: 1, cells, Score));
        await JS.InvokeVoidAsync("sessionStorage.setItem", SessionKey, json);
    }
    catch (JSException) { }              // 隐私模式禁用存储：功能零降级，仅无会话保持
    catch (JSDisconnectedException) { }  // 断线/关页：写入丢失，但下一变更点会再写
}
```

| 写入点 | 时机 | 语义 |
|---|---|---|
| `AfterMove()`（**已有单点**，C-06 引入） | 每步有效移动后 | 保存当前局 |
| `RestartGame()` 末尾 | 重玩 | **覆盖为新局存档（不是清除）** |

> **为什么即时写而不是 Dispose 时写**：手机切后台时 circuit 可能直接死亡，`DisposeAsync` 里的 JS 调用只会拿到 `JSDisconnectedException`——即写即存是唯一可靠时机。每步一次 interop 往返（约 1ms 级）与 C-06 的 best 写入同级，可接受。

> **为什么 RestartGame 是覆盖不是清除**：若清除存档，"重玩 → 立刻切页 → 回来"会恢复成**上一局的残档**（存档没了但也没写入新局）——正确语义是"重玩后进度从新局开始"，覆盖才自洽。

### 3.3 恢复：并入 `OnAfterRenderAsync(firstRender)` 既有分支

```csharp
// 与 best 读取同段（isBestLoaded 判空之后，键盘注册之前）
if (!isSessionRestored)
{
    isSessionRestored = true;
    try
    {
        var json = await JS.InvokeAsync<string?>("sessionStorage.getItem", SessionKey);
        var st = json is null ? null : JsonSerializer.Deserialize<SessionState>(json);
        if (st is { v: 1 } && st.cells.Length == GridSize * GridSize)
        {
            for (int i = 0; i < st.cells.Length; i++)
                board[i / GridSize, i % GridSize] = st.cells[i];
            Score = st.score;
            isGameOver = IsGameOver();          // 重算，不信任存档
            StateHasChanged();                   // 把恢复的盘面刷出来
        }
        // 无存档/版本不符/损坏 → 保持 OnInitialized 的初始新局，静默
    }
    catch (JSException) { }
    catch (JsonException) { }                    // 半截 JSON → 新局
}
```

- **顺序敏感**：`OnInitialized` 先跑了 `RestartGame`（开局盘），firstRender 恢复在渲染后覆盖它——所以**恢复成功后必须 `StateHasChanged()`**；
- 预渲染首帧仍是新局，恢复后毫秒级补齐——与 best/键盘同一 trade-off（06/14 文档已确立该模式），可接受；
- 恢复到死局（存档即 game over）→ `IsGameOver()` 重算为 true → 结束遮罩自然出现，**无需特判**。

### 3.4 与 C-06（best）的协同

| | best | 进度 |
|---|---|---|
| 存储 | localStorage | sessionStorage |
| 生命周期 | 永久（跨会话） | 本次访问 |
| 重玩 | 不清（纪录保留） | 覆盖为新局 |
| 读取 | firstRender 同分支 | 同分支先后执行 |

两者互不感知；恢复残局后若其分数 > best，`UpdateBestScore` 语义不变（只增不减），不会出现恢复旧局把 best 刷爆的副作用——旧局分数必然 ≤ 当时已写入的 best。

## 6. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 手机切后台被系统杀掉浏览器进程 | sessionStorage 随进程消失，无法恢复 | 属"本次访问"语义之外的冷启动，无法避免也无需求；文档如实声明边界 |
| 每步一次 interop 写入 | 弱网下略增延迟感 | 写为 fire-and-forget 不阻塞移动渲染；实测 1ms 级 |
| 恢复闪帧（预渲染新局 → 恢复旧局） | 轻微视觉跳动 | 与 best 同模式，历史上无感知 |
| 存档 schema 演进 | 旧档错解 | `v` 版本号 + 长度校验，不符即弃 |
| 重玩语义实现错误（清而未覆盖） | 回来恢复出已重玩的旧局 | §3.2 已钉死"覆盖"；e2e 断言 4 专门守它 |

**回退**：还原 `Game_2048.razor` 单文件；sessionStorage 残键无需清理（无存档路径天然容错）。
