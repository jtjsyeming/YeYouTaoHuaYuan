### 1.1 阻塞①的机理

`SessionState.Cells` 在 L74 声明为 `int[]?`，注释明确写着"缺字段的合法 JSON 会走到这条分支，必须靠模式匹配挡掉而非 NRE"——那是 D-17 踩过的坑。v1.0 的 `IsValidArchive` 第一行把它**重新踩了一遍**：

```
{"v":1}  →  反序列化后 Cells == null, V == 1
         →  st is not { V: 1 } 为 false（V 匹配成功，不再短路）
         →  求值 st.Cells.Length  →  NullReferenceException
```

而 L406-409 的 `catch` 只列了 `JSException / JsonException / JSDisconnectedException / ObjectDisposedException`——`NullReferenceException` 不在其中，异常直接冒泡出 `OnAfterRenderAsync`。Blazor Server 对未处理异常的处理是**断开 circuit**，用户看到的是"An unhandled error has occurred. Reload"。

**正确写法**：结构闸继续用 D-17 的嵌套属性模式（`Cells` 为 `null` 时**匹配失败**而不是抛异常），通过后再把非空的数组交给内容校验函数。

### 1.2 阻塞②③的共同根源：分数缺一个"可证上界"

v1.0 用 `4,000,000` 这个绝对上限，等于承认"分数没有可判定的约束"。事实不是——分数是可以从盘面反推上界的（见 §3.2），而这条上界既能让 FT-01 第 5 类被拒，也顺带堵掉阻塞③：**伪造分在入口就进不来，`Score` 里根本没有 999999，"走一步后再污染"这条路径不存在**。

## 2. 修复方案

三道闸调整为：

| 闸 | 作用 | 相对 v1.0 |
|---|---|---|
| 闸一 结构 + 内容校验（含分数上界） | 根修 P-002 / P-004 / P-005，**同时根修 P-003 的伪分入口** | 校验函数重写（加分数上界、修 NRE） |
| 闸二 恢复路径零 best 副作用 | 关掉"恢复即写 best"这条通路 | 保留，但明确它**只是第二道**，单靠它会假绿 |
| 闸三 运行期空盘自愈 | —— | **删除**（不可达 + 与《19》冲突） |

### 2.1 闸一：结构闸沿用 D-17 的嵌套模式

```csharp
// 结构闸：Cells 为 null 时**匹配失败**，不会 NRE（v1.0 的 `st.Cells.Length` 会在这里炸 circuit）
if (st is { V: 1, Cells.Length: GridSize * GridSize })
{
    if (!IsValidArchive(st.Cells!, st.Score))
    {
        // 内容非法（P-002/004/005）：清掉脏档，避免每次进页面重复拒绝；棋盘保持 OnInitialized 的新局
        await JS.InvokeVoidAsync("sessionStorage.removeItem", SessionKey);
    }
    else
    {
        // …原恢复体（见 §2.4）…
    }
}
```

`st.Cells!` 的 `!` 是有依据的：长度模式已通过 ⇒ `Cells` 非 `null`。

### 2.2 闸一：内容校验函数（含分数上界）

```csharp
private const int MaxTileValue = 1 << 17;   // 131072：4×4 棋盘的 2 的幂上界

/// <summary>存档内容校验（P-002/004/005）。结构闸已在调用点用过嵌套属性模式，故 cells 必非 null。
/// 三条判据：① 每个非零块是 [2, 131072] 内的 2 的幂；② 至少有一块（全零盘拒 → P-004 根治）；
/// ③ 分数不超过由盘面可证的合并上界（见 §3.2 推导）→ 伪高分在这一条被拒，P-003 的入口随之关闭。</summary>
private static bool IsValidArchive(int[] cells, int score)
{
    if (score < 0) return false;

    var hasTile = false;
    long scoreCap = 0;
    foreach (var v in cells)
    {
        if (v == 0) continue;
        if (v < 2 || v > MaxTileValue || (v & (v - 1)) != 0) return false;   // 非 2 幂 / 越界
        hasTile = true;
        scoreCap += (long)v * (BitOperations.Log2((uint)v) - 1);             // v == 2 时贡献 0
    }

    return hasTile && score <= scoreCap;
}
```

- `BitOperations` 在 `System.Numerics`，razor 顶部需补 **`@using System.Numerics`**（全仓此前未引用）。不想加 `using` 的等价写法：`int k = 0; for (var t = v; t > 1; t >>= 1) k++;`（最多循环 17 次）。
- 全程用 `long` 累加：`scoreCap` 理论最大 3,932,164，虽在 `int` 范围内，但用 `long` 免掉"将来改棋盘尺寸要回来重算"的隐患。
- **非 2 幂（3/6/7/`int.MaxValue`）→ 拒 → P-005 的输入源头消失**，`Merge` 不会再产出 6 或 -2；
- **全零 → 拒 → P-004 根治**，空盘档进不了棋盘；
- **负分 / 超上界 → 拒**。

### 2.3 闸二：恢复路径零 best 副作用

删除 L401 的 `UpdateBestScore();`（连带那句注释 L382-383 一并改）。**只删这一行，不动 `UpdateBestScore` 本身**——`AfterMove()` L100 的调用才是破纪录的唯一合法来源。

删掉后，恢复分支里 `isBestLoaded` 与恢复的先后顺序不再影响 best（原《现状》§208 记录的那条"硬性顺序"理由随之失效，见 §7 同步清单）。仍建议保持"先读 best、后恢复"的代码顺序：改顺序没有收益，反而会让阅读者误解两者仍有依赖。

**已确认的副作用**：`localStorage` 清空但 `sessionStorage` 尚存时（罕见），恢复后会出现"分数 5000 / 最高分 0"的瞬间不一致。**不额外处理**——下一次有效移动时 `Score > BestScore(0)` 成立，`UpdateBestScore` 立刻把 best 补齐，且 G2048-35（预置 500、恢复不改写纪录）不受影响。

**为什么单靠闸二不够（阻塞③）**：删掉 L401 之后，`Score` 仍等于 999999。玩家按一下方向键 →
`MoveLeft` → `AfterMove` → `UpdateBestScore()` → `999999 > 0` → `WriteBestAsync` → `localStorage = 999999`。
FT-02 只在"恢复后"读一次状态、**不走子**，所以这个洞开着它也 PASS。v2.0 的 G2048-38 因此增加"走一步后再查 `localStorage`"的第二段断言。

### 2.4 闸三：删除

v1.0 §2.3 的"`AfterMove` 内加一行空盘自愈"**不实施**，理由两条：

1. **不可达**：空盘下任一方向 `Merge` 输出全 0 → `IsBoardChanged` 为假 → L94 早退，自愈行永远执行不到。要生效必须插在早退**之前**，那等于把一次 16 格扫描塞进每一步走子的热路径，为一个"闸一之后不可达"的状态买单。
2. **与后续实施冲突**：《19》（P-006/P-007）要把 `MoveXxx ×4` 与 `AfterMove` 改成 async 并抽出 `RestoreSessionAsync`；18 只应改恢复分支与新增静态成员，**不碰 `AfterMove` 的签名**，才能给 19 留出干净的重构面。

## 3. 分数上界的推导与验证

### 3.1 推导

把棋盘上每个块看成一棵**合并树**：叶子是 spawn 出来的 2（或 4），每次合并 `x + x → 2x` 产生一个内部结点，结点值 = 2x = 该次合并的得分增量。

- 全部 spawn 都是 2 时，一棵最终值为 `v` 的树共有 `log₂v − 1` 层内部结点，每层贡献之和恰为 `v` ⇒ 该树对总分的贡献 = `v · (log₂v − 1)`。
- 不同终局块的树**互不相交**（一个块只由一次合并产生，其两个输入不再属于别的块）。
- 因此 **`score ≤ Σ_{v≠0} v · (log₂v − 1)`**，等号在"全部 spawn 都是 2 且无浪费"时取到。
- **4 点 spawn 只会让实际分数更小**（它跳过了一次合并），所以该界对 90/10、乃至任意 spawn 策略都成立。

### 3.2 三重验证（本次实测）

| 验证 | 结果 |
|---|---|
| 反算"完美终局盘" `131072, 65536, …, 4` | cap = **3,932,164**；文献的理论最大分 **3,932,156**，差 8 恰是最末那个 4 若由 spawn 产生不贡献分数 —— 公式自洽，也说明 v1.0 的 `4,000,000` 取值方向对但**不能当判据** |
| 300 局随机对局、120 万状态，逐状态比 `score > cap` | **0 次违反** |
| 伪造档 `cells=[2,4]`、`score=999999` | cap = **4** ⇒ 拒（这正是 FT-01 第 5 类需要的判据） |

结论：这是一条**紧的可证上界**，不是启发式。用它做判据不会误杀任何真实对局；而绝对上限 4,000,000 会放行 999999。

### 3.3 常数收敛

`MaxScoreValue` 删除：上界由盘面推出，全局最大 3,932,164，不需要第二个真值来源。`MaxTileValue` 保留（2 的幂判据要用）。

    test.info().annotations.push({ type: 'G2048-37', description: JSON.stringify(rows) });
  });

  test('G2048-38 伪高分不污染 localStorage（含走一步之后）', async ({ page }) => {

    await expect.poll(async () => sig(await readBoard(page)), { timeout: 7000 }).toBe(sig(b));

## 6. 误杀风险与残余边界（如实登记）

| 项 | 说明 | 处置 |
|---|---|---|
| 上界公式依赖"标准 2048 规则" | 若将来引入分数加成/道具，或把 `GridSize` 改成 5，`v·(log₂v − 1)` 不再成立 | 在方法注释里写清推导前提（§2.2 已带），改动规则时必须同步；G2048-42 会先红 |
| `MaxTileValue = 131072` | 5×5 棋盘的合法上界更高 | 与 `GridSize` 一起改，别单独动 |
| "可信伪造"仍会被接受 | 例如盘面 `1024` + `score=9000`：cap = 9216，合法；走一步后 best 仍可能被抬到 9000+ | **不修**——它与"用户真的打到 9000 分"在数据上不可区分。本条登记为已知边界，不要再为它加启发式 |
| 恢复后"最高分 < 当前分"的瞬间 | 仅发生在 `localStorage` 被清而 `sessionStorage` 尚存时 | 不处理：下一次有效移动即自洽（§2.3） |
| `{"v":2}` 等结构坏档不清键 | 与 D-17 一致；`xyz` 走 `catch (JsonException)` 分支，清理需另加一处 | 本次不做；若要统一，注意两处都要清 |
