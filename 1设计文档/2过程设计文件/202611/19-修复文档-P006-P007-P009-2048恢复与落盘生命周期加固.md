# 19 - 修复文档：P-006/P-007/P-009 2048 恢复与落盘生命周期加固

> 来源：《3测试报告/2026-11-06.md》§6.1 P-006 / P-007 / P-009　|　日期：2026-11-06　|　状态：待实施
> 合并理由：三条同属"**异步恢复/落盘与用户操作的时间窗竞争**"，修复都落在恢复时序与保存管线（`Game_2048.razor` 同一段生命周期代码）
> 对应 FT 证据：FT-08（重玩被旧档覆盖 5/5）、FT-07（立刻刷新丢最后一步 10/10）、FT-09（首屏闪烁）

## 1. 三条问题与根因链

| 编号 | 现象 | 根因 |
|---|---|---|
| P-006 | 预渲染/恢复窗口内点"重玩"→ 分数轨迹 `0 → 40`，**重玩被旧档撤销**，最终回到残局 | `OnAfterRenderAsync` 先开闸（UI 已可点）再 `await getItem`；窗口内 `RestartGame()` 写了新档，恢复分支随后用**已读到的旧值**覆盖 `board/Score` |
| P-007 | 点方向键后**立刻** reload，10/10 丢最后一步；等 DOM 更新再 reload 则 8/8 保持 | `AfterMove` 的 `_ = SaveSessionAsync()` fire-and-forget：`setItem` interop 尚未完成时整页刷新断开 circuit |
| P-009 | 预渲染 HTML/首帧为新局（2 块、0 分），Blazor 就绪后跳成残局 | `ServerPrerendered` 模式固有：预渲染实例跑 `OnInitialized` 出新局 HTML，交互实例 `OnAfterRenderAsync` 才恢复 |

三者叠加成真实用户最易触发的路径：**慢网看到"假新局"（P-009）→ 以为进度丢了点重玩（P-006）→ 重玩被旧档撤销**；而"点完立刻刷新丢一步"（P-007）是同一异步管线的另一端。

## 2. 修复方案

### 2.1 会话就绪门闸（主修 P-006 + 缓解 P-009）

```csharp
private bool isSessionReady = false;   // 恢复完成前 UI 处于"加载中"
```

- **markup**：`game-container` 绑定 `@(isSessionReady ? "" : "session-loading")`；"重玩"按钮 `Disabled="@(isGameOver || !isSessionReady)"`；
- **css**：`.session-loading { pointer-events: none; opacity: .6; }`——恢复窗口内棋盘半透明且**点不动**；
- `RestoreSessionAsync` 末尾（无论恢复成败）`isSessionReady = true; StateHasChanged();`；
- 效果：预渲染首帧用户看到的是"半透明、不可点"的盘面而非"可以玩的假新局"——**P-009 从"误导"降级为"加载指示"**，同时窗口内重玩点击根本到不了服务端（P-006 的 pointer 路径被掐断）。

### 2.2 重玩与恢复互斥（键盘路径兜底，P-006 补刀）

`pointer-events` 挡不住 `gamekeyboard.js` 的 window 级键盘监听，故补标志互斥：

```csharp
private bool restartRequested = false;   // RestartGame() 内置位（一次性）
// RestoreSessionAsync 覆盖 board 前：
if (restartRequested) return;            // 窗口内用户已重玩 → 丢弃恢复，尊重用户操作
```

互斥规则：**恢复让位于重玩**（用户显式动作 > 自动恢复），`isSessionReady` 仍置 true。

### 2.3 落盘纳入事件处理管线（主修 P-007）

四个 `MoveXxx` 改 `async Task`，`AfterMove` 改 `async Task` 并把落盘从 fire-and-forget 改为 **await**：

```csharp
private async Task AfterMove(int[,] boardBefore)
{
    // …既有：无变化早退 / AddRandomTile / UpdateBestScore / IsGameOver…
    await SaveSessionAsync();        // ← 原 `_ = SaveSessionAsync()`
    StateHasChanged();
}
```

- Blazor 事件处理器 await 后仍在同一同步上下文，`StateHasChanged` 安全（与 D-03 ticker 的 `InvokeAsync` 模式同理）；
- 效果：`setItem` 指令在**事件消息处理完成前**发出，丢失窗口从"处理后空闲期"压缩到"单个 SignalR 往返内"；
- **必须如实声明物理极限**：若浏览器在 `setItem` 指令到达前就导航（用户手速快于一个往返），该步**任何客户端方案都保不住**——这是 Blazor Server 架构边界，不是缺陷。P-007 的修复目标是"窗口减半 + 行为可预期"，不是归零。

### 2.4 配套测试口径修正（P-007 判据）

- 保留断言："等渲染出该步再 reload → 100% 保持"（**门禁判据**）；
- "零等待 reload"降级为**观测项**（允许偶发丢失，只监控不判红）——否则门禁会在物理极限上假红，重蹈 P-001 覆辙。
