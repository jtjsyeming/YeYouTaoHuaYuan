## 1. P-015 的定量结论

### 1.1 为什么"零余量"

```css
.tetris-container { min-height: 100vh; }                       /* 桌面 */
@@media (max-width: 520px) {
    .tetris-container { min-height: calc(100dvh - 74px); }     /* 手机：74 = 导航 56 + .content padding-top 17.6 */
}
```

`min-height` 被**精确配平**到「文档高 = 视口高」，所以七档手机视口实测 `scrollHeight == clientHeight` 一个像素都不差（D-14 当初就是按这个配平定下来的）。**任何高度的元素插在容器前面都会 1:1 变成纵向溢出。**

### 1.2 实测（同一台机、同一进程，仅 DOM 差异）

| 视口 | 基线 `scrollH/clientH` | 插入默认 `h1` 后 | 增量 | 正常字号 / 外高 |
|---|---|---|---|---|
| 320×568 | 568 / 568 | **608** / 568 | +40.2 | 26.8px / 32.2+8 |
| 375×667 | 667 / 667 | **708** / 667 | +41.1 | 27.625px / 33.1+8 |
| 520×900 | 900 / 900 | **943** / 900 | +43.8 | 29.8px / 35.8+8 |
| 1280×800 | 818 / 800（**基线即 +18**） | 874 / 800 | +56 | 40px / 48 |

两点附带结论：

1. **字号是 rfs 流式的**（26.8 / 27.625 / 29.8 / 40px 随视口变），所以「插入一个固定 px 的补偿」不可能对上——**必须先把 h1 的高度钉死**，再让容器扣同一个常数。
2. 桌面 1280 基线已有 17.6px 纵向溢出（容器 `100vh` 叠加在 `padding-top:17.6` 之下），`D-14` 不覆盖桌面档，属**既有**、本批不处理（见 §6）。

### 1.3 v1.0 的"白字"为什么是隐形

| 探针 | 值 |
|---|---|
| `document.body` 背景 | `rgb(255, 255, 255)` |
| `article.content` / `main` 背景 | `rgba(0, 0, 0, 0)`（透明，透出 body 白） |
| `.tetris-container` 背景 | `rgb(10, 10, 10)` |
| `h1` 位置 | top 73.6 → bottom 97.6；容器 top **103.6**（h1 在容器**外面**） |
| `h1` 继承色 | `rgb(136, 109, 104)`（`#886D68`，与 `/game_2048` 的 `<h1>` 同色） |

即：**标题在浅色文档流上、游戏区在它下方**。这与 `/game_2048` 的形态完全一致（`<h1>2048</h1>` 也在 `.game-container` 之外），所以正确做法不是"深色主题适配"，而是**沿用站内既有标题外观**，只把高度钉死。

## 2. 修订后的方案

### 2.1 P-015 正确做法（已实测通过，可直接照抄）

`Tetris.razor` markup：`<PageTitle>` 之后、`.tetris-container` 之前插一行

```razor
<PageTitle>俄罗斯方块</PageTitle>

<h1 class="tetris-title">俄罗斯方块</h1>

<div class="tetris-container">
```

`Tetris.razor` 的 `<style>` 里加类，并**改两处 `min-height`**：

```css
    /* 页面主标题：高度必须确定（24 + 6 = 30px），因为容器 min-height 要按它扣减。
       桌面与 ≤520px 两处 min-height 的 30px 必须与这里同步；改错时 D14-2 会在 7 档视口同时变红。 */
    .tetris-title {
        font-size: 20px;
        line-height: 24px;
        margin: 0 0 6px;
        padding: 0;
        text-align: center;
    }

    .tetris-container {
        ...
        min-height: calc(100vh - 30px);        /* 原 100vh */
    }

    @@media (max-width: 520px) {
        .tetris-container {
            ...
            min-height: calc(100dvh - 74px - 30px);   /* 原 calc(100dvh - 74px)；30 = 标题行高 24 + 下边距 6 */
        }
    }
```

理由与边界：

- **为什么钉死 20px/24px 而不是沿用 rfs 默认字号**：见 §1.2 第 1 条。默认 h1 外高在 320→1280 之间从 40.2 漂到 56，`calc()` 里没法跟。钉死后实测七档 h1 外高恒为 **30.0px**。
- **为什么 `text-align:center`**：≤520px 时容器 `margin:0 -24px` 是满宽的，标题若左对齐会缩进 24px、与满宽黑块左右不对称；居中后与棋盘轴线一致。若更想与 `/game_2048` 的 27.6px 左对齐标题完全同构，把 `font-size` 改大时**必须同步改两处 30px**——不改就红（见下）。
- **耦合是被门禁兜住的，不是靠注释兜住的**：任何人改 h1 字号/行高却没同步扣减，`D14-2` 会在 7 档同时红。这是本方案唯一可依赖的护栏，所以**不需要**再新增 h1 高度断言（见 §4.3）。

**实测（真实代码，非注入）**：

| 视口 | `scrollW/clientW` | `scrollH/clientH` | h1 外高 | 四键最大底边 |
|---|---|---|---|---|
| 320×568 | 320/320 | **568/568** | 30 | 500.1 |
| 360×640 | 360/360 | **640/640** | 30 | 500.1 |
| 375×667 | 375/375 | **667/667** | 30 | 520.7 |
| 390×844 | 390/390 | **844/844** | 30 | 543.2 |
| 414×896 | 414/414 | **896/896** | 30 | 579.1 |
| 460×800 | 460/460 | **800/800** | 30 | 649.4 |
| 520×900 | 520/520 | **900/900** | 30 | 664.7 |
| 1280×800 | 1280/1280 | 818/800（与基线一致） | 30 | 731.6 |

`D-14` 的右栏判据同样未受影响：`panel.right − canvas.right = 8.0`（≥0）、`panel.top − canvas.top = 0`（同排）。

### 2.5 P-008 表述修正 + FT-06 判据同步

**两处文案**（不改代码、不改行为）：

`更新记录.md:68`（D-17 条目）与 `现状.md:216`（§3.4 第 4 条之后）都是这句话，统一改为：

> 关键实证理由是多标签隔离：`sessionStorage` 按标签页分桶——**全新标签各自独立**；`window.open` 与「复制标签页」会**克隆**开启者的会话存储（HTML 规范行为），两个标签从同一残局各自开局、**此后写入互不影响**。`localStorage` 是 origin 级共享，A 标签玩到一半时 B 标签开一局就会互相覆盖。

**两句都实测过**（Chromium，真实存档键 `jtjsym.g2048.session`）：

| 断言 | 实测 |
|---|---|
| `window.open` 克隆会话 | A 走了 4 步后存档 59 字节 `{"v":1,"cells":[0,2,4,4,...],"score":4}`；popup 打开后 `sessionStorage` **完全相同**，渲染出同样的 5 块 / `分数：4` |
| 后续写入互不影响 | A 写 `probe.k = A-after`、B 写 `probe.k2 = B-only` → A 看不到 `probe.k2`，B 拿到的 `probe.k` 仍是 `A-before`；全新 `browser.newContext()` 里两个键都不存在 |

**必须同步改 `Test/functiontest.mjs` 的 FT-06**（v1.0 完全没提，不改就是永久红）：

```js
  return {
    // 判据随文档口径变更：规范行为就是"克隆"，因此"继承"才是应当成立的那一侧；
    // 并且要额外证明"继承之后各写各的"——这才是 sessionStorage 与 localStorage 的真实差别。
    pass: !!popup && !!b && sb.session === sa.session && sb.probeIndependent === true,
    expect: 'window.open/复制标签会克隆 sessionStorage（规范行为）：新标签从同一残局开局，且此后两标签的写入互不影响',
    actual: { a: {...}, popup: b && {...}, freshContext: {...}, errors: errs.slice(0, 3) },
    kind: 'observe',
  };
```

其中 `sb.probeIndependent` 需要 popup 侧做一次「写自己独有的键、再回读」的小探针（约 4 行）。**这是判据随文档口径变更，不是放宽**——旧判据断言的是"不该继承"，而该断言从未反映过产品意图，只反映了一句写错的文档；新判据比旧判据**更强**（多验一条写隔离）。

## 6. 残余与明确不做

| 项 | 结论 |
|---|---|
| 1280 桌面 `scrollH 818 / clientH 800` | **基线即有**（容器 `100vh` 叠在 `padding-top:17.6` 之下），D-14 不覆盖桌面档；本批把 `100vh` 改成 `calc(100vh - 30px)` 只是让 h1 的 30px 不进这个缺口，**没有修也没有扩大** |
| 320px 下 h1 与满宽容器左右不齐 | h1 内缩 24px（article padding）、容器 `margin:0 -24px` 满宽。居中后视觉可接受，但白条与黑块的横向边界确实不齐 —— **如实登记，不为此改布局** |
| `<h1>` 与站点其它页字号不一致 | `/game_2048` 的 h1 是 rfs 流式（27.6~40px），`/tetris` 固定 20px。原因是 1.2 节：容器 `min-height` 视图口，标题高度必须可计算。若将来把 tetris 容器改成非 `100vh` 方案，可一并统一 |
| FT-06 判据变更 | 属"判据随文档口径修正"，**不是放宽**；下一版报告要写明变更理由，否则会被误读为"为了让报告变绿而改测试" |
| P-011 的数字 | 若团队坚持保留数字，就必须承认这是第 3 次过期；本文件建议删数字，若否决请用 **17** |
| 不做 `@key` | h1 是静态字面量，不参与列表 diff，也没有需要靠 `@key` 保住的 DOM 身份 —— **不需要** |
