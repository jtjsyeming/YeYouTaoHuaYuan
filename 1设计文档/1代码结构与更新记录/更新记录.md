## 2026-11-05　`（未提交）`　爱情计时器日历精确换算 + 年月天副行（D-03 → C-13）

依据《15-开发文档-D03爱情计时器日历精确换算与年月天展示-v2.0.md》实施：

- **两件事一起做掉**：换算口径由 365/30 近似改为**日历逐级扣减**（`AddYears` → `AddMonths` → 余数天），同时把「只算不展示」的 `ElapsedTimeYear/Months/Day` 三个死属性删掉，改为每行主计时下一条 `.timer-calendar` 副行；`ElapsedTimeInfo` 只剩 `ElapsedTime` + `CalendarText`。
- **clamp 交给 BCL**：周年/月纪念日未到各回退一次，所以 `m--` 不会到 −1；闰日 2-29 在非闰年收敛 2-28，1-31 跨 2 月落 2-28。**没有抄《06》§7.1 的 `DiffYmd`**——它按"借贷"处理，`2023-01-31→2023-03-01` 会给出 `(0,1,−2)`（负天数）、`2020-02-29→2021-02-28` 给出 `(0,11,30)`。
- **格式化跳过所有零段**：只跳前导零会得到"8 年 0 个月 14 天"。实际规则：`8/6/14 → 8 年 6 个月 14 天`、`8/0/14 → 8 年 14 天`、`8/0/0 → 8 年整`、`0/6/0 → 6 个月`、`0/0/0 → 不到 1 天`。
- **取舍**：不加"共 N 天"——主行已有 `N 天, X 小时…`，`TotalDays` 与主行同源恒等，副行会把同一个数说两遍；里程碑提醒留到后续（那时再加属性与渲染方）。
- **两个必须记住的坑**：① 副行**只能带 `.timer-calendar`**——加 `timer` 会让 LT-01 的 `div.timer===3` 在 `test:lt`/`test:smoke` 双套件同时红，加 `timer-display` 会撞 D-12 的"不裁切"断言；② `color` 必须显式写 `#e48bfa`，副行是 `.timer` 的**兄弟**节点，`color:inherit` 只会拿到祖先 `div` 的褐色 `#886D68`（首版正是这么写的，实测副行呈褐色，与粉色主行不搭，已改）。
- **间距**：桌面 `margin:-14px 0 12px`（主行 `.timer` 下边距 20px）→ 实测距上一条主行 **6px**、距下一条 **32px**；≤520px 该断点 `.timer-display` 的 margin 是 8px，故用 `-4px 0 10px`。`@@media` 的双 @ 是 Razor 语法要求，不是笔误。
- **新增 `LT-25~30`**（`tools/e2e/tests/d03_calendar.spec.mjs` + `npm run test:d03`，39.5s）：三行副行齐备且主行未变 / 今天·昨天·7 天前 / 闰日与月末 clamp / 内置相识日自洽 / 秒级副行恒定 / 375px 不溢出。期望值**不写死**，由 Node 侧独立实现（`clampAddYears`/`clampAddMonths`）对当天现算——与 `g2048` 的 `simulate` 同一范式，闰日与月末这些边界才真正被覆盖。

## 2026-11-03　`d516ca1`　2048 最高分持久化（D-16）+ G2048-24~29 自动化

依据《14-开发文档-2048最高分机制-v2.0.md》实施：

- **问题**：2048 刷新或重开后分数归零，没有任何历史参照。
- **存储**：`localStorage['jtjsym.g2048.best']`，站内首例存储调用（全仓此前无 `localStorage`/`sessionStorage`）。走 Blazor 的点分路径 interop（`window.localStorage.getItem/setItem`），**不新建 JS 文件**；键名带 `jtjsym.` 前缀，后续 Tetris 可直接复用同一约定。
- **判定点只加 1 行**：`AfterMove()` 里 `IsBoardChanged` 早退之后、`AddRandomTile()` **之前**调 `UpdateBestScore()`。四个 `MoveXxx()` 里并没有 `AddRandomTile()`，统一收口在 `AfterMove`——按钮与键盘两条通道天然共用；`RestartGame` 不经过它，重开不会误写。
- **展示用独立 `<p class="best-score">最高分：N</p>`**，不并进「分数：」那一行：D02-12 是硬锚定 `/^分数：\d+$/`，同 `<p>` 追加文本会立刻把这条 P0 门禁打红。
- **生命周期拆两段**：原来"读最高分"和"键盘注册"共用一个 `keyModule` 条件，现各自幂等（`isBestLoaded` / `keyModule`），键盘代码以后怎么改都不牵连最高分加载。
- **fire-and-forget 的 catch 必须补 `ObjectDisposedException`**：关页/电路释放时 `InvokeVoidAsync` 会抛，漏了就是未观察异常污染日志。读失败（隐私模式/存储被禁）恒 0、写失败静默 → 功能零降级，只是不持久化；损坏值走 `int.TryParse` 视为 0。
- **新增 `G2048-24~29`**（`tools/e2e/tests/d16_best_score.spec.mjs` + `npm run test:d16`，20.4s）：读取 500 / 容错 `abc` / 写入落盘 / 刷新保持 / 重玩保持 / 跨路由保持。两条测试设计要点：预置值**只在键不存在时**写——`addInitScript` 每次导航（含 `reload`）都会重跑，无条件写会把刚存的值冲掉，让"刷新后保持"变成恒真假绿；落盘断言一律 `expect.poll`，因为 `setItem` 是异步的。
- **验证**：Release `--no-incremental` 构建 0 警告 0 错误；`test:d16` 6/6、`test:g2048` 6 通过 1 跳过、`test:d02` 11 通过 1 跳过、`test:smoke` 6 通过 1 跳过，全绿。

## 2026-11-03　`8d024af`　D-01 新块生成概率标准化（50/50 → 90/10）+ G2048-23 自动化

依据《13-开发文档-D01新块生成概率标准化-v2.0.md》实施，代码只改 2 行：

- **问题**：`Game_2048.razor` 的 `AddRandomTile()` 用 `random.Next(1, 3) * 2` 取值，在 `[1,3)` 上均匀 → 2 与 4 各 50%；标准 2048 是 **90% 出 2、10% 出 4**（4 的频次是标准的 5 倍，每步注入的期望值 3.0 vs 标准的 2.2，等于凭空降低难度）。
- **改法**：`@code` 顶部加常量 `FourSpawnPercent = 10`，取值行改为 `random.Next(100) < 100 - FourSpawnPercent ? 2 : 4`——百分制整数抽样，2 恰占 90 个取值、4 恰占 10 个，无浮点误差；想调比例只动这一个常量。位置抽样 `emptyTiles[random.Next(count)]` 本就均匀、不动；`AfterMove` 的 `IsBoardChanged` 早退与合并逻辑一概未碰。
- **明确不改 `Random.Shared`**：那会关掉"注入固定种子"的可能，与后续抽 `Game2048Core` 做确定性 xUnit 的路线冲突；Tetris 用它是因为从不需要复现序列。
- **新增 `G2048-23`**（`tools/e2e/tests/d01_spawn.spec.mjs` + `npm run test:d01`）：连点「重玩」50 局，只统计初始两块的取值（100 个独立样本，不掺走棋逻辑）。上界 25/100 是 μ+5σ——回退到旧代码 μ=50 会落到 −8.3σ 必红；下界 ≥1 的误报率 ≈2.7e-5；`test.slow()` 放开 60s 默认超时（实测 16.4s）。
- **实测**：改前用同一手法 50 局 100 样本，4 占 **49.0%**；改后 **9.0%**（91 个 2 / 9 个 4），每局恒 2 块、取值域无异常。
- **验证**：`dotnet build --no-incremental` 0 错误 0 警告；`test:d01` 1/1、`test:g2048` 6 通过 1 跳过（G2048-04/05/19/20 仍待抽离 `Game2048Core`）、`test:smoke` 6 通过 1 跳过（TRIS-23 人工项）全绿。执行前已重启实例——`reuseExistingServer: true` 会复用旧 `dotnet run`，旧 IL 仍是 50/50，否则必假红。
