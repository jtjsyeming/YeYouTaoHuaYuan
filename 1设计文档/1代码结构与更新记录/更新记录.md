## 2026-11-07　`（未提交）`　LoveTime 可见性监听补 `pagehide` 收尾（`NF-06` Firefox 红 → C-33）

在实施《25》的门禁回归中发现的**既有回归**：`npm run test:nf` 的 `NF-06`（遍历 6 页控制台无红色异常）在 Firefox 下稳定失败 3/3，Chromium 不受影响。改动面仅 `wwwroot/js/lovetimer.js`（3 处、约 10 行），`LoveTime.razor` 与计时逻辑未动。

- **报错内容**：`Cannot send data if the connection is not in the 'Connected' State.`（`blazor.server.js`），即"连接已断仍要发送"。
- **根因（实测事件序列，不是推测）**：Firefox 整篇卸载时的派发顺序为 `beforeunload` → **Circuit 断开** → `pagehide` → `visibilitychange(hidden)` → `unload`。最后那个 `hidden` **不是"用户切走标签"**，而是文档正在销毁；`lovetimer.js` 的 handler 此时仍挂在 `document` 上，于是对已断开的电路发一次 `invokeMethodAsync` → 框架先打一条控制台红错，`.catch()` 只能吞掉 Promise 拒绝、吞不掉这条日志。这也解释了为什么 `test:d08` 全绿而 `NF-06` 红：D08-1~3 用 `defineProperty` 造后台、**不卸载文档**，走不到这条路径。
- **修法**：`register()` 同时挂 `window.addEventListener('pagehide', ...)`，触发即**同步**摘掉 `visibilitychange` 监听（纯 JS，不发任何 interop —— `pagehide` 早于 `visibilitychange`，赶得上）；`removeListener()` 一并清 `pagehide`，`unregister(id)` 的 `id === currentId` 护栏语义不变。
- **A/B 因果证据**：把《24》对 `LoveTime.razor` 的改动 `git stash` 回 HEAD（并把 `lovetimer.js` 移出 wwwroot）重建 → 同一 6 页遍历 **0 红错 3/3**；恢复《24》→ **稳定 1 条**。故该红由《24》（C-29）引入，与本批样式域改动无关。
- **诊断中排除的两条假设**：① 不是 `DisposeAsync` 里那两发 `unregister` / `module.DisposeAsync` —— 临时注释掉后 `NF-06` 仍红 3/3；② 不是 `site.css` / `Counter.razor` 的改动 —— 本批只改类名与注释，且基线（无 class 改动）复现相同。
- **验证**：`NF-06` **3/3 绿**（两个 project 均过）、`test:nf` **19 通过 4 跳过 0 失败**、`test:d08` **3/3** 无回归、`dotnet build` 0 警告 0 错误。

- **v1.0 的方案主体对、API 全错**：本页的秒刷是 `PeriodicTimer` + `async Task` 循环 + `CancellationTokenSource`，**没有 `ticker` 字段、没有 `Stop()`/`Start()`**（那是 `System.Timers.Timer` 的面貌）。可行路线只有两条：标志位跳过，或 Cancel 后重建 CTS。选前者 —— 后者必须**成对**把 `tickerCts` 置 `null`（`StartTicker()` 的守卫是 `tickerCts is not null`，漏置就再也不启动、静默失效），且 `using var timer` 的释放是异步的，新旧循环会有同一 tick 并存的窗口。
- **`if (isHidden) continue;` 的位置是判据的一部分**：必须放在 `InvokeAsync` **之前**。放进 `InvokeAsync` 内部的 lambda 里只能省掉 `RefreshAll`+`StateHasChanged` 的计算，**进渲染上下文就必然推一帧**，网络侧等于没改。代价是后台仍每秒唤醒一次线程池（D-08 要归零的是帧，不是空转）；`isHidden` 声明 `volatile`（JS 回调线程写、ticker 线程读）。
- **`IDisposable` → `IAsyncDisposable` 是结构性改动，不是加个接口**：本页原先只实现 `IDisposable`，加 interop 后必须改异步版本；而渲染器此后**只调 `DisposeAsync`**，原 `Dispose()` 会静默变死代码（D-19 陷阱）。故保留 `Dispose()`（那里才是 `isDisposed = true` + 停 ticker）并由 `DisposeAsync` **首行**调用。两发 interop（`unregister` / `module.DisposeAsync`）**各用一个 `try`** —— 共用一个时前者抛出会跳过后者、JS 侧对象引用表漏一项（《21》C-25 实测）。
- **`OnAfterRender(bool)` → `OnAfterRenderAsync(bool)`，顺序钉死"先启 ticker、后 await import"**：`import` 要 await，而相位 φ（tick 相对整秒的偏移）从"页面开始交互那一瞬"起算 —— 先 await 会让 φ 跟着一次 interop 往返漂移，LT-31 的相位对齐前提随之变化。`import` 之后仍**复检 `isDisposed`**（import 期间组件可能已被销毁，那时 `visModule` 还是 `null`，`DisposeAsync` 什么都没卸），命中则释放模块 + 释放 `DotNetObjectReference` 并 return。

依据《16-开发文档-D17-2048对局进度会话保持-v2.0.md》实施，业务改动全部在 `jtjsym/jtjsym/Pages/MyPage/Game_2048.razor`：

- **选型 `sessionStorage['jtjsym.g2048.session']` 而非 `localStorage`**：语义是"本次访问"——切页/刷新/切后台都在，关标签即清。关键实证理由是多标签隔离：`sessionStorage` 按标签页分桶——**全新标签各自独立**；`window.open` 与「复制标签页」会**克隆**开启者的会话存储（HTML 规范行为），两个标签从同一残局各自开局、**此后写入互不影响**。`localStorage` 是 origin 级共享，A 标签玩到一半时 B 标签开一局就会互相覆盖。存档 JSON 为 `{"v":1,"cells":[16 个行优先整数],"score":N}`——`int[,]` 不能直接序列化（`NotSupportedException`），必须扁平化；**不存 `isGameOver`**，恢复后用 `IsGameOver()` 重算，单一事实源。
- **`isSessionReady` 一个字段担两责，是本次唯一的"必须这么写"**：`_Host.cshtml` 是 `ServerPrerendered`，`OnInitialized` 跑两次、每次都 `RestartGame()`；若在 `RestartGame` 末尾无条件落盘，交互实例那一跑会把**刚生成的新开局**写进存档、覆盖用户上次残局，紧接着的恢复读到的就是这份新开局 —— 症状是"功能看起来做完了却恢复不出来"，且不报错不抛异常。故闸门放在 `SaveSessionAsync()` 第一行（恢复启动前一律 `return`），开闸放在恢复分支第一行，两处必须是同一字段。**不能靠 catch 兜底**：预渲染实例里 JS 调用抛的是 `InvalidOperationException`，不是 `JSException`。`RestartGame` 因此无需拆分、两处 `@onclick` 零改动。
- **`AfterMove` 是 `void`，写入用 `_ = SaveSessionAsync();`**（与 D-16 的 `_ = WriteBestAsync()` 同款）：`await` 会 CS 编译失败，`async void` 会把异常抛进渲染树终止 circuit。安全性来自快照在第一个 `await` 之前已完成序列化，任务晚完成不会读到后来的盘面。
- **恢复段必须排在"读最高分"之后（硬性顺序）**：反例是 `localStorage` 里 best=500，若先恢复，`BestScore` 还是字段初值 0，恢复出的 `Score=100` 会被 `UpdateBestScore` 判成破纪录，把真实纪录**改成 100**。`Score <= BestScore` 只防"变小"，防不了"基准未加载"。恢复末尾补一次 `UpdateBestScore()` 使两者自洽。
- **重玩是"覆盖"不是"清除"**：清除会让"重玩 → 立刻切页 → 回来"得到第三块随机盘，用户看到的是"重玩被撤销了一半"。覆盖才自洽——重玩后的第一屏原样回来。
- **坏档容错靠模式匹配而非 NRE**：`Cells` 声明为 `int[]?`，判据写 `st is { V: 1, Cells.Length: GridSize * GridSize }`——缺字段的**合法 JSON**（`{"v":1}`）反序列化后 `Cells` 为 null，写成 `st.Cells.Length` 会抛 NRE 而 `catch` 只列了 `JSException`/`JsonException`，NRE 会一路冒到 circuit。
- **测试**：新增 `tools/e2e/tests/d17_session.spec.mjs`（G2048-30~36）+ `npm run test:d17`，`helpers.mjs` 加 `SESSION_KEY`/`readSession`。往返类用例一律比**盘面签名**（16 格按行拼接），不只看"2 块 / 0 分"——恢复失败时新开局形态与期望完全一致，只比形态等于恒真；G2048-33 另加"新局签名 ≠ 旧局签名"的自检。
- **`test:d16` 的 G2048-27 随本次一并改写**：它原本断言"破纪录后刷新 → `分数：0`"，与 D-17 的目的正面冲突，不改则门禁必红。现改为"刷新后进度与最高分均保持"——是需求语义变了，不是让测试迁就代码。
